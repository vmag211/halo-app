## What this package is, and what it deliberately leaves out

One GET, consumed by one screen. `const read=useProductionResource<ForecastSnapshot>('forecast.read',{date,place},!!date);` (W: `components/production/WeekSources.tsx:13`), whose only caller is Plan outdoors (W: `components/expanded/WeekOutdoors.tsx:31`). No route exists (`ls app/api` has no `forecast`), so the planner today shows "This service is unavailable. Try again later." and "Retry forecast" in production, and saves every plan with `'Forecast unavailable. Recheck official conditions before going.'` (W: `WeekOutdoors.tsx:38`).

**In scope:**

- `GET /api/forecast?date=YYYY-MM-DD&place=<free text>` answering the `ForecastSnapshot` the validator accepts (W: `WeekSources.tsx:11,15-17`), for the household's saved home or a typed North Carolina county, city, town, CDP or ZIP code.
- Census internal-point coordinates for every gazetteer place kind, through `scripts/build-nc-places.mjs` (F2, Task 1).
- Three free providers, each with a timeout, a cache keyed by rounded point and hour, and a budget: Open-Meteo (weather, heat as feels-like temperature, UV), EPA AirNow forecast (air, daily), NWS active alerts (the "Official notices" row only).
- An Upstash Redis cache with an in-memory first layer. **No migration** (F22): nothing is written to Postgres, so 0026 stays free.

**Dropped, with reasons:**

- **Pollen.** No free pollen forecast covers North Carolina: Google Pollen is excluded by D-F2, and Open-Meteo's pollen is "Only available in Europe during pollen season with 4 days forecast" (open-meteo.com/en/docs/air-quality-api, retrieved 2026-10-19). Every period carries `pollen: null`, rendered "Unavailable", and `coverage.Pollen` says why (F15). *Unblocked by:* a free source with US coverage.
- **`changedMessage`.** Never emitted (F20). The request carries no prior version, so the server cannot know what the person saw (digest 10.7). *Unblocked by:* a contract change that sends the version the person saw, or server-held previous issues (storage).
- **The NWS hourly forecast and Open-Meteo modelled air.** D-F2 assigns weather to Open-Meteo and air to AirNow; a second source per factor would need its own provenance channel the contract lacks (one `source`, one `coverage` string per factor).
- **Cache warming.** No cron prefetch over places or homes: the AirNow FAQ asks users not to build forecast databases through the web services (F6), and BE-289 wants refresh "on stale reads, not once per household request" (spec:817), which a read-through cache already is.

**Blocked, not planned:**

- **Places outside North Carolina by name.** The gazetteer is NC only (W: `lib/places.js:1-50`). A home outside NC is still served by its stored point (F1). *Unblocked by:* a wider gazetteer, the same Census files for other states.
- **A numeric air value inside each period.** AirNow's forecast is daily and its guidelines forbid altering it (F6). *Unblocked by:* Yogi labelling the Air row "daily" the way Pollen is (Open question 5).

## Rulings (binding on every task)

- **F1, place (D-F1).** `place` is trimmed with JavaScript's `trim`. Empty means the household's saved home: `profiles.lat`/`lng` for the verified user, owner-scoped, labelled "your home area" and never named or echoed. `X-Halo-Home-Context` is ignored, as B05 D5 and B06 H2 do (MP-331: "Home location can be the default", spec:2239). No stored home gives an empty snapshot (F21) whose coverage says to finish setup or type a North Carolina city, county or ZIP code. A non-empty `place` is resolved by `resolveForecastPlace` (Task 2), **exact matches only, never prefix, never fuzzy, never Mapbox**, in this order:
  1. Every standalone five-digit run (a ZIP+4 keeps its first five) that is an NC ZCTA in the gazetteer. Exactly one distinct ZCTA wins outright. Two or more distinct is `ambiguous`. Five digits that are not an NC ZCTA, with nothing else matching, is `unmatched` with the reason "not a North Carolina ZIP code".
  2. Otherwise the text is split on commas and semicolons. A segment naming another US state (its postal code or full name, a fixed 50-entry table) makes the answer `outside`. A final `NC` or `North Carolina` segment is dropped. Each remaining segment is matched exactly against county keys (with or without "County"/"Co.") and place keys (bare and full display name), using `lib/places.js`'s own normalisation, through a new `exactPlaces(text)` export (Task 1), so "Columbus County" never matches the town (W: `lib/places.js:26-31`).
  3. Of the distinct candidates, the most specific kind wins (ZCTA, then place, then county). One left is `matched`; more than one is `ambiguous` (for example "Fairview", two places; or "Durham, Chapel Hill").
  Segments that match nothing are ignored once another matches, so `Environmental Learning Center, Charlotte, NC 28202` (the handoff test's own value, W: `test/ui/production-outdoor-handoff.spec.ts:36`) resolves to ZIP 28202, and "Freedom Park, Charlotte" to Charlotte. Because the snapshot has no place field (trap 21), the resolved label is stated in `source` and at the start of every coverage string (F15, F16), so a forecast for Charlotte's internal point is never presented as Freedom Park's. `unmatched`, `ambiguous` and `outside` answer an empty snapshot with no provider call and no limiter token, which is what makes keystrokes free: "Char", "Charl" and "Charlo" cost one gazetteer scan each, and the first exact match costs at most one cached provider round.
- **F2, coordinates (Task 1).** `lib/data/ncPlaces.json` gains `lat` and `lng`, rounded to 3 decimals (the home's precision), on every place and ZCTA, and a new `counties: [{geoid, lat, lng}]` array from the county Gazetteer. `lib/places.js` gains `placePoint(id)` returning `{lat, lng}` or `null`. Candidates returned by `searchPlaces` and `placeById` keep exactly their five fields: `locations.search`, `explore.area` and 0022's stored copy are unchanged (W: `lib/places.js:16-24`).
- **F3, rounding sent out.** Every provider call and every cache key uses the point rounded to **2 decimals** (about 1.1 km), coarser than anything stored and finer than the GFS grid (0.11 degrees, open-meteo.com/en/docs/gfs-api). The cron already shares NWS lookups at this precision (`const key = \`${lat.toFixed(2)},${lng.toFixed(2)}\`;`, W: `app/api/cron/daily/route.js:171`); B10 also sends the rounded point, which the cron does not.
- **F4, sources (D-F2).** Weather and heat (feels-like temperature) and UV: Open-Meteo. Air: AirNow forecast under `AIRNOW_API_KEY`. Official notices: NWS active alerts, free and keyless ("open data, free to use for any purpose"), used only for `warningStatus`; Vibhav may strike it (Open question 3), in which case `warningStatus` is the frontend's own fallback, `'Warnings unavailable. Check the official site.'` (W: `WeekOutdoors.tsx:46`). Pollen: none (Dropped). Not called: Google Pollen, OpenUV, Mapbox, NWS forecast, Open-Meteo air quality. `lib/dailyReadings.js` is not edited and none of its inner closures is reused: none is a forecast, and `getJson` has no timeout (`const res = await fetchImpl(url, init);`, W: `lib/dailyReadings.js:118`). Editing it would touch `/api/daily-score`, the cron and backfill (digest 10.5).
- **F5, the Open-Meteo request.** `https://api.open-meteo.com/v1/forecast?latitude=<2dp>&longitude=<2dp>&hourly=temperature_2m,apparent_temperature,precipitation_probability,weather_code,wind_speed_10m,uv_index&models=<pinned>&timezone=auto&timeformat=unixtime&forecast_days=8&temperature_unit=fahrenheit&wind_speed_unit=mph`. **`timeformat=unixtime`** makes every timestamp an absolute UTC instant, so the offset-less local strings that void the whole snapshot (trap 15; `/Z$|[+-]\d{2}:\d{2}$/`, W: `WeekSources.tsx:15`) never enter the code, and the fixed-offset DST caveat does not apply to instants. `timezone=auto` is kept only for the response's IANA `timezone` (the home's zone, F12). **One pinned model**: the GFS global model, because `uv_index` is "GFS only" and a seamless blend (`ncep_gfs_seamless` combines HRRR and GFS) has two run times and so no single honest issue time. Task 4 copies the exact `models` value and its metadata link from the Model Updates table and records both, with the retrieval date, in the adapter header. The metadata call is made beside every forecast call (it is not counted against limits).
- **F6, the AirNow forecast.** Request by rounded point with `distance=25` (the observation call's radius, W: `lib/dailyReadings.js:147`), exact URL and whether `date` is required taken from the authenticated docs capture (Task 5 gate). Parsing: trim `DateIssue` and `DateForecast` and require `YYYY-MM-DD`; keep `ReportingArea`, `StateCode`, `ParameterName`, `AQI`, `Category.Name`, `ActionDay` (DS-033, spec:1072); `AQI` of `-1`, missing or non-finite means **category only**, never a number; a category outside AirNow's six names is dropped as not available. **Values are reported as received** (guidelines): each pollutant's category and number listed, the highest named, nothing averaged, nothing spread across hours. Because the forecast is daily and the Air row has no "daily" label (W: `WeekOutdoors.tsx:45`), **every period's `air` is `null`**, and the daily forecast appears in `coverage.Air` and in each period's `tradeoff` (F14). `Discussion` is not used. Credit is given in `coverage.Air` (F15). The API key travels in the query string, so an adapter error never carries the URL; only the status code and a fixed reason are logged.
- **F7, NWS alerts.** `https://api.weather.gov/alerts/active?point=<2dp>,<2dp>` with `User-Agent` from `NWS_USER_AGENT` (default `HALO/1.0`, the existing value, W: `lib/dailyReadings.js:13`; a maintained contact is Open question 3, DS-041 spec:1088). A new parser (`lib/forecast/nwsAlerts.js`) keeps every feature with `status: 'Actual'` and `messageType` `Alert` or `Update`, drops those whose `ends ?? expires` is past, and keeps the NWS `event` name as received. **A failed, timed-out or unparseable lookup is a failure, never an empty list.** The cron's helper is not reused: it turns any failure into `[]` (`.catch(() => [])`) and keeps only flood and heat (W: `app/api/cron/daily/route.js:169-182`; W: `lib/alertInputs.js:11-24`). `warningStatus` strings (F23): none active, "No National Weather Service alerts are active for this area as of 14:20 EDT. Check the official site before going."; some, "Active National Weather Service alerts: Heat Advisory, Flood Watch. Check the official site."; failure or budget, the frontend's own fallback. Alerts describe **now**, not the planned date, and say so ("are active", "as of"). The cron's lossy helper is recorded for its owner (N5), not fixed here.
- **F8, timeouts and the route budget.** Every outbound call uses `AbortSignal.timeout`: Open-Meteo forecast 6 s, its metadata 3 s, AirNow 6 s, NWS 6 s, all four in parallel, no in-request retries, response bodies capped at 2 MB. `export const maxDuration = 15` (Next.js 16 segment config, `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/02-route-segment-config/maxDuration.md`), under the client's 20 s (`setTimeout(abort,input.timeoutMs ?? 20_000)`, W: `lib/frontend/production/runtime.ts:116`). GET handlers are dynamic by default since v15 (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md:669`); the response also sets `Cache-Control: private, no-store`. A superseded keystroke request is aborted only in the browser (digest 1, W: `components/production/ProductionContext.tsx:12-15`); the server deliberately does not abort its provider calls on client disconnect, so the fetch still fills the cache the next keystroke reads.
- **F9, cache.** Provider data is cached, never the snapshot: snapshots are assembled per request (cheap, pure) so `expiresAt` and the date always fit the request. Layers: per-instance memory, then Upstash Redis through `@upstash/redis` `Redis.fromEnv()` resolved lazily as `lib/waterGeo.js` does (W: `lib/waterGeo.js:126-160`), then the provider. Keys: `halo:forecast:v1:<provider>:<lat2>,<lng2>:<YYYYMMDDHH UTC>` for Open-Meteo (forecast plus its metadata) and AirNow; NWS alerts add a ten-minute slot to the hour (`...:<YYYYMMDDHH>:<0-5>`), because a warning an hour stale is worse than a forecast an hour stale. Values: the normalised provider data plus `fetchedAt`, never a household id, never the typed text. Redis TTL 2 h (alerts 20 min); memory holds at most 500 entries. Single-flight per key per instance. **Negative cache:** a provider failure is remembered for 60 s under the same key with a `failed` marker, so a burst of keystrokes resolving to one point and a quick "Retry forecast" do not hammer a failing provider. A Redis failure is a miss, logged once per instance per minute, never a 5xx.
- **F10, budgets and limiters** (new in `lib/ratelimit.js`, sliding windows, each beside its rationale):
  - `forecastOpenMeteoDailyLimiter`, 3,000 per 24 h, and `forecastOpenMeteoMinuteLimiter`, 200 per minute, global, **fail-closed**. A third of the 10,000 daily and 600 per minute free limits, because `/api/daily-score` and the cron spend the same free quota (W: `lib/dailyReadings.js:160,174`). `FORECAST_OPEN_METEO_DAILY_LIMIT` overrides the daily number (the `ASSISTANT_GLOBAL_DAILY_LIMIT` precedent, W: `lib/ratelimit.js:52`). Refused: 503 with `Retry-After` (F21).
  - `forecastAirNowLimiter`, 200 per hour, global, fail-closed: under the reported 500 per hour per key, leaving room for the observation calls the cron and daily-score make with the same key. Refused: `coverage.Air` says air was not checked; the rest of the snapshot is served.
  - `forecastNwsLimiter`, 600 per hour, global, fail-closed. Refused: the `warningStatus` fallback.
  - `forecastHouseholdLimiter`, 30 per hour keyed `forecast:<profileId>`, **fail-open** (the critical-path rule, W: `lib/ratelimit.js:74-78`), counted **only** when a request would reach at least one provider after both caches miss. Never the daily-score limiter, whose key and one-per-five-minutes shape would 429 the second date a person picks (W: `lib/ratelimit.js:62`; trap 18). Refused: 429 with `Retry-After`.
  Globals fail closed because they protect a shared free quota whose terms bind HALO, and degrading the feature is what BE-303 asks: "degrade the affected feature when a budget is reached" (spec:838). During an Upstash outage memory-cached points are still served; misses answer 503.
- **F11, no capability flag (D-F3, the spend part).** BE-351 wants server-enforced flags "where they change writes, provider spending or data processing" (spec:918). B10 writes nothing, spends nothing (every source is free), and its only quota exposure is bounded server-side by F10, which already degrades honestly. A flag-off route would look the same to the client as an outage. The env override in F10 is the operational kill switch: set to 0, every miss answers 503. The terms questions (Open questions 1 and 2) gate **production use**, not the build; `/api/daily-score` already calls both providers under the same terms, so B10 changes volume, not posture.
- **F12, horizon semantics (D-F3, closeout decision 4: "agree date-only versus instant bounds", W: `docs/product/HALO_BACKEND_WIRING_CURRENT.md:120`).** **Date-only.** `horizonStart` and `horizonEnd` are `YYYY-MM-DD` local dates in the snapshot's `zone`, both inclusive, describing the dates on which this snapshot can carry periods (periods exist only with Open-Meteo weather, so this is the weather horizon). `horizonStart` is today in `zone`. `horizonEnd` is the last local date, at most today plus 6 (seven dates; BE-094 "do not promise seven days" is honoured by computing it, not asserting it), on which all three period windows have complete hourly temperature and weather code. It depends on the place and the provider fetch, **never on the requested date**. The client's `draft.date>live.data.horizonEnd.slice(0,10)` (W: `WeekOutdoors.tsx:32`) is then an exact string comparison of two local dates with no zone or DST arithmetic. Per-factor horizons (HO-086, MP-334 "No promise that all factors cover the same seven days") live in `coverage` (F15): UV the same as weather; Air the dates AirNow actually issued. Zone: a gazetteer place's own `timezone` (`America/New_York`, W: `lib/places.js:62,88`); the home's from Open-Meteo's resolved `timezone`, accepted only if `new Intl.DateTimeFormat('en',{timeZone})` accepts it (as the client checks, W: `WeekSources.tsx:16`), else no periods and a 503. Empty snapshots carry the policy horizon (today through today plus 6) in `America/New_York`, the gazetteer's zone, and coverage says no forecast was made.
- **F13, periods.** Local windows in `zone`: **Morning 08:00 to 12:00, Afternoon 12:00 to 17:00, Evening 17:00 to 21:00** (contiguous, so a long activity is covered; none contains the 02:00 transition hour, so no window is ever gapped or doubled). Each bound is converted from local wall time to a UTC instant with an `Intl`-based zoned conversion and emitted as `YYYY-MM-DDTHH:MM:SSZ`, which passes the offset regex and `Date.parse`. Instantaneous variables (temperature, feels-like, weather code, wind, UV) use hours `start <= t < end`; precipitation probability, a "preceding-hour" value (open-meteo.com/en/docs), uses `start < t <= end`. Per period: temperature low and high, highest feels-like, most severe WMO weather code by an explicit severity rank, highest rain chance, highest wind, highest UV rounded to one decimal. A period is **omitted** if its end is at or before now, or if any of its hours lacks temperature or weather code; `uv` is `null` if any hour lacks UV. Missing never becomes zero; a real modelled UV of 0 in the evening is reported as 0. A requested date before today, after `horizonEnd`, or with no complete period answers `periods: []` with full metadata (F21), so the client shows `forecastUnavailable` or, past the horizon, `future` and its check-again date (W: `lib/frontend/week-evidence-preview.ts:19,22`; MP-333).
- **F14, `weather` and `tradeoff` text.** Built from a frozen template table, no U+2014, no "safe" or score (MP-332, spec:2241). `weather`: "64 to 71 °F (18 to 22 °C), partly cloudy, feels like up to 72 °F, rain chance up to 20%, wind up to 9 mph" (the °C figures are arithmetic on the provider's values, not a second source; units are Open question 6). `tradeoff` compares this period with the others present on UV, feels-like temperature and rain chance ("Lowest UV of these periods. Cooler than the afternoon.") and then always states air: "Air is a daily AirNow forecast: Moderate for the whole day, the same for every period." or "No air forecast for this date." Never empty.
- **F15, `coverage`.** Always exactly the four keys the screen reads, `Air`, `UV`, `Pollen`, `Weather` (W: `WeekOutdoors.tsx:46`), **every value a string** (trap 16: the validator only checks `!!value.coverage`, W: `WeekSources.tsx:15`, and an object would crash the render). Each begins with the resolved place ("For Charlotte, NC (Census internal point):", "For your home area:", "For ZIP 28202, NC (Census internal point):") and states provider, basis and resolution, issue and horizon. - **F16, `source`.** One string naming every contributing provider and the place, for example "Open-Meteo, EPA AirNow and the National Weather Service, for Charlotte, NC". Review conditions before going.` (W: `WeekOutdoors.tsx:38`), so the saved task keeps where its forecast was for. A provider that contributed nothing is not named.
- **F17, `issuedAt` (DS-038, spec:1082; trap 6 of the brief).** Populated snapshots: the pinned Open-Meteo model's `last_run_initialisation_time`, as an ISO UTC instant. Never retrieval time, never `generationtime_ms`. The metadata is read immediately before and after the forecast call; if the two disagree, or the forecast call started less than 10 minutes after `last_run_availability_time` (the docs' own wait), the run behind the data is not known, nothing is cached, and the answer is 503 with `Retry-After` until the window closes. AirNow's `DateIssue` and NWS times appear in coverage, never as `issuedAt`. **Empty snapshots** (no forecast at all): `issuedAt` is the time HALO issued that empty answer, documented in the OpenAPI as such; the screen prints "Issued" only inside the periods branch (W: `WeekOutdoors.tsx:44`), so it is never displayed as a forecast issue time.
- **F18, `expiresAt`.** Populated: the earliest `fetchedAt` among the Open-Meteo and AirNow data used, plus 90 minutes. - **F19, `version`.** Snapshot: `fc1-` plus the first 16 hex of sha256 over canonical JSON of the resolved place id (or `home`), `zone`, the horizon, the requested date, the Open-Meteo run initialisation time and the hourly values used, the AirNow rows used, the set of NWS alert ids, and a code constant `FORECAST_RULES_VERSION`. Excluded: `fetchedAt`, `issuedAt` of an empty answer, `expiresAt`, "as of" times. So unchanged content keeps its version across re-fetches and the confirm step never shows a false "This plan or its forecast changed" (W: `WeekOutdoors.tsx:32,35`). Period `version`: a readable provenance label written into the saved task's history and reason (`:36`, `:38`), "Open-Meteo GFS run 2026-10-19T12Z; AirNow 2026-10-19" or the Open-Meteo part alone. - **F20, `changedMessage` is never emitted.** Its presence forces a review (`const changed=live.production?!!live.data?.changedMessage:`, W: `WeekOutdoors.tsx:32`); nothing honest can fill it without a prior version.
- **F21, status taxonomy.** 200 with a populated snapshot; 200 with `periods: []` and full valid metadata for a definitive "no forecast" (no home, unmatched, ambiguous or outside place, past date, beyond the horizon, no complete period); **400** for `date` missing, not `YYYY-MM-DD` or not a calendar date, and for `place` over 100 characters (the input's own `maxLength={100}`, W: `WeekOutdoors.tsx:42`) or containing control characters, through `parseText` (W: `lib/validate.js`); 401 without a session; **429** with `Retry-After` from F10's household limiter; **503** with `Retry-After` when Open-Meteo failed, timed out, was refused by its budget, returned an unacceptable zone or an unknown run (F17), or the profile read failed.
