## Global constraints (every task, every reviewer)

- **Read the installed Next.js docs first.** `AGENTS.md`: this Next.js (16.3.6) has breaking changes. Before writing or changing any route file, read the relevant guide under `node_modules/next/dist/docs/` (route handlers, dynamic route params, `after`). Dynamic route `params` may be a Promise.
- **Identity comes only from the verified bearer token** (`requireUser`). Never from body, query or header ids. A client-supplied id is only ever a lookup key combined with the owner filter.
- **Additive, compatible responses.** Keep every existing field name and status code that the approved frontend (`lib/frontend/api.ts`, `lib/api.js`) depends on. New fields are added, not renamed. The existing `error` string field stays on every error body.
- **No em dashes (U+2014) in any new string that can reach the app** (error messages, copy, labels). Code comments and docs are free to avoid them too.
- **No production access.** Do not read `.env*`, do not call the production URL, do not connect to any Supabase project, do not run `scripts/smoke-test.mjs` (it seeds a database and can run the cron). All verification is local: `node --test`, in-memory fakes, PGlite.
- **Migrations** are numbered after `0014` (`0015_*.sql`, ...), idempotent (safe to re-run), commented in the style of the existing files, and the routes that use them **degrade cleanly until the migration is applied** (existing repo convention). The user applies migrations by hand in the Supabase SQL editor; never claim a migration is applied.
- **No secrets in fixtures or docs.** Only synthetic ids and values.
- **Tests:** plain `node --test`. The package script is `node --test test/*.test.mjs`, which only picks up top-level `test/*.test.mjs`, so every new test file lives there; helpers live in `test/helpers/` or `test/db/`. Test output must be pristine (no stray warnings).
- **Gate before every commit:** `node --test test/*.test.mjs && npm run typecheck && npm run lint` all green (lint: 0 errors; warnings that already existed are fine). If typecheck fails with odd `"<name> 2"` or missing module errors, it is the iCloud duplicate-file problem: `ls node_modules/@types | grep " "`, then `rm -rf .next && npm ci`; do not debug code for that.
- **Commits:** conventional style (`feat(backend): ...`, `test(backend): ...`, `docs(backend): ...`). **Do not add any `Co-Authored-By` trailer or any Claude attribution line** (the user's standing rule). Commit only; do not push, merge or change branches (the controller pushes).
- **Scope discipline:** do only what the task lists. Note out-of-scope findings in the report; do not fix them.
- **Truthfulness rules from the spec:** unknown is not zero; a mock is not a live integration; HTTP 200 is not correct semantics.

### Task 1: Error envelope and request validation primitives

Pure modules, no route changes. Files: create `lib/apiErrors.js`, `lib/validate.js`, `test/apiErrors.test.mjs`, `test/validate.test.mjs`. Modify `lib/serverAuth.js` only so `authErrorResponse` delegates to the new envelope (details below).

**`lib/apiErrors.js` (pure, no imports from serverAuth)**

- `ERROR_CODES`: `bad_request`, `validation_failed`, `auth_required`, `auth_unavailable`, `forbidden`, `not_found`, `conflict`, `payload_too_large`, `rate_limited`, `upstream_unavailable`, `internal_error`, `feature_unavailable` (each key upper-snake, value as listed).
- `requestIdFor(request)`: returns the incoming `x-request-id` header when it matches `/^[A-Za-z0-9._-]{8,64}$/`, otherwise `crypto.randomUUID()`.
- `apiError({ status, code, message, fieldErrors, retryable, retryAfterSeconds, requestId })` returns a `Response` with JSON body `{ error: message, code, message, field_errors, retryable, request_id }` and headers `X-Request-Id` and, when `retryAfterSeconds` is a positive integer, `Retry-After`. `field_errors` is always an array of `{ field, code, message }` (empty array when none). `retryable` defaults to `true` for status 429, 502, 503, 504 and `false` otherwise; an explicit boolean overrides. `requestId` defaults to a fresh UUID.
- `validationError(fieldErrors, requestId)`: status 400, code `validation_failed`, message = first field error's message, or `Some details need another look.` when the array is empty.
- `internalError(requestId)`: status 500, code `internal_error`, message `Something went wrong on our side. Please try again.`, retryable true. Never includes a database or provider message.
- `authFailureResponse(status, message, requestId)`: 401 becomes code `auth_required` (not retryable); 403 becomes `forbidden`; 503 becomes `auth_unavailable`, retryable, `Retry-After: 2`; any other status becomes `internal_error`. Message passes through unchanged.
- In `lib/serverAuth.js`, `authErrorResponse(error, requestId)` keeps its signature (second arg optional) and returns `authFailureResponse(error.status, error.message, requestId)` for an `AuthError`, `null` otherwise. Existing callers must keep working unchanged, and existing messages are kept verbatim.

**`lib/validate.js` (pure)**. Every parser returns `{ ok: true, value }` or `{ ok: false, code, message }` (never throws on bad input). Messages contain no em dashes.

- `parseIsoDate(value, { min = '2000-01-01', max = null } = {})`: accepts only a string matching `^\d{4}-\d{2}-\d{2}$`, rejects non-calendar dates (`2026-02-31`, `2026-13-01`, `2025-02-29`, accepts `2024-02-29`), enforces `min` and `max` when given (string compare on valid ISO dates). Codes: `invalid_date`, `date_out_of_range`.
- `parseDateRange({ from, to }, { today, defaultDays = 90, maxDays = 366, min = '2000-01-01', maxFutureDays = 1 })`: `from`/`to` are strings or null/undefined. Missing `to` becomes `today`; missing `from` becomes `to` minus `defaultDays - 1` days. `to` may be at most `today + maxFutureDays`. `from` must be `<= to`. The inclusive span must be `<= maxDays`. Returns `{ ok: true, value: { from, to } }` or `{ ok: false, fieldErrors: [{ field, code, message }] }` with codes `invalid_date`, `date_out_of_range`, `range_inverted`, `range_too_large`. `today` is required (tests pass a fixed date); use the repo's `addDays` from `lib/localDate.js`.
- `parseCoordinates({ lat, lng })`: accepts finite numbers or numeric strings, rejects null, undefined, empty or whitespace-only strings (the `Number('') === 0` trap), arrays, booleans, `NaN`, `Infinity`, `lat` outside [-90, 90], `lng` outside [-180, 180]. Returns numbers. Codes: `invalid_coordinate`, `coordinate_out_of_range`. Reports field errors for `lat` and `lng` independently.
- `parseBoundedInt(value, { min, max, fallback })`: integers only (reject `1.5`, `'1e3'`, `'abc'`), `fallback` used only when value is null, undefined or empty string; out of range is an error, not a clamp.
- `parseEnum(value, allowed, { fallback, caseInsensitive = false })`.
- `parseUuid(value)`: standard 8-4-4-4-12 hex.
- `parseText(value, { maxLength, required = false, trim = true })`: must be a string (not number/object), counts characters by `Array.from(value).length`, rejects over `maxLength` (error, not truncation), empty after trim is an error only when `required`.
- `readJsonBody(request, { maxBytes = 16384 } = {})` (async): returns `{ ok: true, value }` where `value` is a plain object, or `{ ok: false, status, code, message }`. Empty body returns `{ ok: true, value: {} }`. A `Content-Length` over `maxBytes` returns 413 `payload_too_large` without reading. Otherwise read `await request.text()` and measure `Buffer.byteLength`; over the limit is 413 (a lying header cannot bypass). Invalid JSON is 400 `bad_request`. A JSON array, `null`, string or number top level is 400 `bad_request`.

**Tests (TDD: write failing tests first, record RED then GREEN in the report).** Cover every rule above including: each calendar edge, the empty-string coordinate trap, boundary values (`lat` 90 and -90 accepted, 90.0001 rejected), `Content-Length` lie, oversize body, non-object JSON, unicode text length (emoji counted as one character), `authFailureResponse` for 401, 403, 503 and an unknown status (check headers and body), and `requestIdFor` accept/reject of a client header.

**Commit** as `feat(backend): add API error envelope and request validation primitives`.

### Task 3: Cross-identity route isolation suite and fixes

The required B01 test, route half: two identities cannot read, mutate, link or export one another's records through any route that exists today. Files: create `test/routeIsolation.test.mjs`; modify route files only to fix defects the suite finds.

Seed two households, `alice` and `bob`, with distinct marker strings in every owned table the routes touch (`profiles`, `household_bands`, `daily_scores`, `home_risks`, `symptom_logs`, `alerts`, `notification_prefs`, `push_subscriptions`, plus any other table a household route reads, found by grepping `supabaseAdmin.from(` under `app/api`). Then, calling as `alice`:

- Every GET route that returns household data (`profile`, `household`, `history`, `journal`, `journal/findings`, `journal/summary`, `alerts`, `notifications`, `home-guard`, `daily-score`, `account` if it reads) returns none of bob's marker values anywhere in the serialized body.
- Mutations are scoped: `DELETE /api/journal?id=<bob's entry id>` returns `deleted: 0` and bob's row is still present; `DELETE /api/journal?all=true` removes only alice's rows; `POST /api/journal` and `POST /api/journal/retrospective` write rows owned by alice even if the body carries `profile_id` or `id` of bob; `PUT /api/household` and `PATCH /api/profile` change only alice's rows.
- Linking: any route accepting a `profile_id` (legacy) returns 403 when it is bob's; `POST /api/push/subscribe` with an `endpoint` that already belongs to bob must neither reassign bob's subscription to alice nor reveal that it exists (record the observed behaviour; if it reassigns, that is a defect to fix: a unique endpoint owned by another identity must not be taken over); notification and alert dismissal by another owner's id changes nothing and does not reveal existence (same response shape as a missing id).
- No route returns a different status or body for "exists but not yours" versus "does not exist" where an id is supplied (no existence leak).
- Identity from the token only: query/body `profile_id`, `user_id`, `id` and headers like `x-user-id` never change whose rows are read.
- Account deletion: `DELETE /api/account` as alice removes alice's rows in every owned table (via the fake's cascade declaration, which you must keep in sync with the real migrations' cascades) and leaves bob's intact.

Intake audit hint (verify, do not assume): `push/subscribe` upserts on the globally unique `endpoint` column (`0010` line about `endpoint text not null unique`), which can reassign another identity's subscription to the caller. Every other household route is believed to scope by `profile_id` already; the suite must prove it rather than rely on that belief.

For each defect the suite exposes, make the smallest route fix and list it in the report (file, line, what leaked, fix). If a route needs a larger change that belongs to another task, record it as deferred instead. Tests assert on behaviour, not only status codes. ### Task 4: Harden read and query routes

Apply Task 1 primitives to every route that reads. Files: modify the route files under `app/api` listed below; create or extend `test/routes*.test.mjs` files using the Task 2 harness (group by route family; keep each test file focused).

Routes: `history`, `journal` (GET, DELETE), `journal/findings`, `journal/summary`, `daily-score`, `home-guard`, `map`, `district`, `learn`, `volunteer`, `alerts` (GET), `notifications` (GET), `sources`, `profile` (GET), `household` (GET), `health`.

Rules to apply to each (read each route first; skip a rule that has no input to validate and say so in the report):

1. **Dates.** `from`, `to`, `days`, `entry_date` query values go through `parseIsoDate`/`parseDateRange`/`parseBoundedInt`. History default stays 90 days and `days` max stays 365; explicit `from`/`to` span is capped at 366 days (`maxDays: 366`); an invalid or inverted range is a 400 `validation_failed` with `field_errors`, never a silent default. `today` is `localDate()` (household-local).
2. **Coordinates.** `lat`/`lng` on `daily-score` and any other route go through `parseCoordinates`. A request with only one of the pair is a 400. Missing both keeps current behaviour (use stored home).
3. **Overrides.** `home-guard` overrides (`county`, `pwsid`, `water_source`, `home_year`) are validated (length caps, enum via the existing `normalizeWaterSource`, `validateHomeYear`); a malformed override is a 400, not ignored. Overrides must not expose another household's private data (they never read other owners' rows; assert it).
4. **Ids.** Any `id` query param is validated with `parseUuid` and returns 400 when malformed.
5. **Errors.** Replace every `NextResponse.json({ error: err.message }, { status: 500 })` and similar leaks of database or provider messages with `internalError(requestId)` after `console.error` of the real error (log line includes the request id). Auth failures use `authErrorResponse(err, requestId)`. All error responses carry `code`, `field_errors`, `retryable`, `request_id`.
6. **`X-Request-Id`** header on every response from these routes (success and error), derived with `requestIdFor(request)`.
7. **Directory error states** (HO-066): `volunteer`/`learn`/`map`/`district`/`sources` distinguish a true empty result from an unavailable backing table (missing table or migration returns the documented degraded body today; keep it, but add `unavailable: true` plus `reason` where today it silently returns an empty list that could be mistaken for "no results"). Do not change what the frontend reads today; additive only.
8. **Bounded reads.** `history` and `journal` GET queries get an explicit row limit (history: 5000 rows, journal: 2000 rows, both well above the 366-day cap with duplicates) and the response carries an additive `truncated: boolean` that is true when the limit was hit, so PostgREST's silent max-rows cap cannot hide data. `district` must not ignore a failed profile read (a read error is a 500 envelope, not an empty household). `volunteer` today returns 200 with an empty list and a note when the database errors: keep the 200 for compatibility but add `unavailable: true` and `reason: 'directory_unavailable'`, so "no organizations match" and "the directory failed" are distinguishable.
9. **Compatibility.** Existing success response shapes are unchanged except additive fields. Add tests proving the old fields are still present.

Tests: per route, one passing case with the legacy request, one per invalid-input rule above, one for the error envelope shape, one proving `request_id` header equals the body's `request_id`.

**Commit** per route family: `feat(backend): validate and harden <family> routes`.

### Task 5: Harden write routes

Apply Task 1 primitives to every route that writes. Files: modify the route files below; extend or create `test/routes*.test.mjs`.

Routes: `journal` (POST), `journal/retrospective` (POST), `household` (PUT), `profile` (PATCH), `onboard` (POST), `alerts` (POST/PATCH if present), `notifications` (PUT/POST if present), `push/subscribe` (POST/DELETE), `assistant` (POST), `account` (DELETE).

Rules:

1. **Body reading.** Use `readJsonBody` with an explicit `maxBytes` per route (journal 8192, household 2048, profile 2048, onboard 4096, retrospective 65536 because it carries a batch, push/subscribe 4096, assistant 8192, others 2048). Invalid JSON is a 400 `bad_request`; oversize is a 413 `payload_too_large`. This is a deliberate compatibility change for bodies that used to be swallowed as `{}` (for example `PUT /api/household` with garbage used to silently set all seven booleans to false: that data-loss path must end). An empty body still means `{}`.
2. **Field validation.** Dates via `parseIsoDate` with `max` = `localDate()` plus one day tolerance for `entry_date` (future journal dates beyond tomorrow are rejected; `retrospective` dates likewise); `band` and `severity` via `parseEnum` with the existing sets; `symptoms` must be an array of strings, at most 20 items, each at most 80 characters (error, not silent truncation); `note` via `parseText` with `maxLength: 500` (reject over the cap with a field error instead of truncating). `household` PUT: each of the seven keys must be a boolean when present, anything else is a field error (today non-`true` silently becomes false); omitted keys keep the documented replace semantics (omitted becomes false), and that is documented in the response. `profile` PATCH: `home_year` via `validateHomeYear`, `water_source` via `normalizeWaterSource`, unknown keys ignored, at least one recognised key required. `onboard`: `address` must be a string, trimmed, 3 to 200 characters; `request_id` via `parseRequestId` (invalid is a 400 rather than ignored); reject when `address` is an object or array (today `encodeURIComponent` stringifies it).
3. **Errors and request id** exactly as Task 4 rules 5 and 6. `account` DELETE stops returning the raw error message and returns a 500 envelope.
4. **Shared limits.** Create `lib/limits.js` (pure) exporting the journal limits used by the route validation: `JOURNAL_NOTE_MAX = 500`, `JOURNAL_SYMPTOMS_MAX = 20`, `JOURNAL_SYMPTOM_MAX_CHARS = 80`, `JOURNAL_SEVERITIES`, `JOURNAL_BANDS`, `JOURNAL_MIN_DATE = '2000-01-01'`. Task 7 mirrors them in database constraints and a test asserts the SQL and these constants agree.
5. **Retrospective batch bounds.** The raw `entries` array is capped at 100 items (more is a 400 `validation_failed`) before any filtering; each date goes through `parseIsoDate` with `max` = today; invalid or duplicate dates are reported in an additive `rejected: [{ index, date, code }]` list while valid dates still save (compatibility with today's silent drop; per-date batch semantics are redone in B10). The month window cannot span more than 366 days.
6. **Push subscriptions.** `endpoint` must be an `https:` URL whose host is a known Web Push service (suffix allowlist in one constant: `fcm.googleapis.com`, `android.googleapis.com`, `push.services.mozilla.com`, `push.apple.com`, `notify.windows.com`), at most 2048 characters; `p256dh` and `auth` are base64url strings within sane lengths. A subscription whose endpoint is owned by another identity is never reassigned (Task 3 behaviour is kept and tested). The cron job POSTs to stored endpoints, so storing arbitrary URLs is a server-side request risk.
7. **Do not change onboard's geocoding, rate limiting or backfill behaviour** in this task; only its input handling and error shapes. (Home-context changes to onboard come in Task 9.)
8. **Draft preservation (server side).** A rejected write must not modify any row: add a test per route that after a 400 or 413 the fake's tables are byte-for-byte unchanged.
9. **Compatibility.** Legacy valid requests keep the same status and response fields. Test it.

Tests per route: valid legacy request, each invalid-input rule, oversize body, invalid JSON, unchanged-state-after-rejection, envelope shape.

**Commit** per route family: `feat(backend): validate and harden <family> write routes`.
