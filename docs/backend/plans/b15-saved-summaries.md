## Rulings (each "proposed, Vibhav to confirm" unless marked)

- **S15-1, per-version ids.** Every successful prepare creates a new summary with a new server id and `revision: 1`; nothing is ever rewritten (an update trigger refuses it). `summary.read(id)` therefore returns exactly what was saved. A newer summary is a new row; there is no lineage.
- **S15-2, home context precedence.** The summary freezes the household's **current** home context as the server holds it at prepare time (0016's row with `effective_to is null`), or `null` when there is none. The body's `homeContextId` and the `X-Halo-Home-Context` header are checks, never inputs: if either is sent and does not name that current home, the prepare is `failed` `home_changed` ("Your current home changed..."), nothing saved. The commit function checks the current home again under a share lock, so a move in between is the same answer. (A 200 failed receipt rather than a 409, so the person sees why; everything after the claim settles in the ledger.)
- **S15-3, failed, never cancelled (B05 9.4; binding).** Every refusal and every abandoned prepare settles `failed`. The reaper's `abandoned` row is answered with its own sentence. No summary operation is ever `cancelled`.
- **S15-4, retention.** Kept until the person clears all or deletes the account. There is no per-summary delete in the registry, so "deletes them" has no route yet; it lands with a future `summary.remove`. Off by default until confirmed.
- **S15-5, exact selection, exact versions.** Each requested record must be this household's and at exactly the sent revision when it is read and again when it is committed; otherwise `failed` `changed` ("A selected record changed..."), nothing saved. A record entry without a revision is a 400 (production rows always carry one). Records are included in their stored order, filtered only by the person's selection; the server does not re-filter by date (the client already did, `SummaryWorkspace.tsx:66`). `collectionRevisions` is accepted and ignored (B11 W6: collections have no revision).
- **S15-6, scores and factors (revised 2026-10-25, audit F05).** Originally a selected Scores or Factors section was saved with a sentence saying it was not included yet, while the prepare still succeeded; the audit found that read as a dropped selection. Now the prepare composes both from the same code the screens read: Today from the household's newest stored `daily_scores` row for today's local date, rebuilt by `formatDailyPayload` exactly as GET /api/daily-score rebuilds a cached row (no provider call; no row today is "unavailable", never an older day); Homeguard from `homeGuardPayload` (`lib/homeGuardPayload.js`, the computation moved out of GET /api/home-guard unchanged). Both answers go through the screens' `buildStageData`, so a reading linked to an earlier home is dropped and private water reads as the screen shows it (which settles the H01 concern: the summary cannot show a score the screen would not). The line builders are shared with `SummaryWorkspace.tsx` and drift-tested. Each line keeps its source date; the manifest still names records only. A section whose evidence cannot be used is saved as unavailable, and "Omissions and scope" opens with the selected sections against the included ones. No migration: the lines live in the existing `report` jsonb.
- **S15-7, tasks.** The `actions` section is composed from 0023's tasks when `tasks` is on and 0023 is applied, each checked at its revision; otherwise the section says it was unavailable and the omissions say so. Task details (`meta`, including notes) are never included.
- **S15-8, private text.** The opt-ins decide, exactly as the client's preview does: notes only with `notes`, place labels and the home's area (county and state, never coordinates or an address) only with `location`, household categories (from `household_bands`) only with `categories`, attachment names and counts only with `attachments`. Attachment bytes, photo data and file metadata are never read. In the export, the frozen `report` is private text; the title (a fixed purpose), dates, selection, manifest and omissions are not.
- **S15-9, limits.** Body 1,000,000 bytes; at most 500 records per summary; a manifest `asOf` longer than 20,000 characters is saved as null; a saved snapshot at most 2,000,000 bytes as JSON (a read must stay under the 4.5 MB platform limit), else `failed` `too_large`; 200 saved summaries per household, else `failed` `limit` (the commit locks the profile FOR NO KEY UPDATE, so concurrent prepares cannot overshoot). A line longer than 20,000 characters is shortened, and the omissions say so, so no saved line can fail the client's 30,000-character check. Purpose must be one of the four the screen offers.
- **S15-10, unavailable answers.** Flag off (or `workspace` off): list and read the non-retryable 503; prepare a 200 `failed` receipt recorded nowhere (a 5xx would park the id). 0029 or 0017 missing, or any failure before the ledger claim: the same, so no 5xx ever parks an id that was never recorded. 0026 missing is found after the claim, so that prepare is recorded `failed` `unavailable` and replays it. The `summary` reconcile is the 503 while the flag is off.
- **S15-11, ledger.** Domain `summary`, kind `summary.prepare`. The stored receipt is `{status, summaryId}` or `{status: 'failed', reason}`, never report content. The reconcile answers a succeeded operation with the saved snapshot read now; a summary removed since (clear all) is answered `failed` `gone`.

## Answers

- `GET /api/summaries`: 200 `{items: [{id, revision, title, createdAt, homeContextId}], complete: true, unresolvedOperations: [...]}`, newest first, the unresolved list read (and reaped) first.
- `POST /api/summaries`: 200 `{operationId, status: 'succeeded', snapshot}`; 200 `{operationId, status: 'failed', reason, message}`; 200 `{operationId, status: 'pending'|'unknown', message}` for a replay still in flight; 400 malformed body, selection or key; 409 a key reused with different input; 500 for a lost database answer (the client reconciles).
- `GET /api/summaries/detail?id=`: 200 the snapshot; 400 a malformed id; 404 another household's or a missing id (the same answer).
- All three carry `Cache-Control: no-store`. No top-level `data` key anywhere.
