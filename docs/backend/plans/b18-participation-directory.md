# B18 participation directory (`organizations.search`, `opportunities.search`, `opportunities.detail`): plan

Base: `origin/vmag211/backend` at `d0e5200`. Migration number **0032** (needs 0004, nothing newer). Rulings use the prefix **P**. Flag `participation` (`HALO_FEATURE_PARTICIPATION`), off by default.

## Why this was blocked, and what changes

B05 blocked `organizations.search` (`b05-discovery-and-summaries.md:15`, 9.3): `volunteer_orgs` cannot hold what the validator needs, and its cause vocabulary does not match the four interests; filling the gap with empty strings would invent content. Unblocking needed: human-written participation content per organization, a person's verification of each listing, a migration keyed by `volunteer_orgs.id`, a failed read that never looks like "no matches", and a meaning for `complete`. B18 builds the **infrastructure only**: two tables a person fills by hand in the SQL editor, read by three routes that serve **only verified rows**. HALO writes no content. With no verified rows the answers are the honest empty states below; an unreadable directory is a 5xx, never `items: []`.

## The frontend contract found

Any 5xx on a GET is `unavailable`; 404 is `unavailable`; 400 `validation`; 429 `rate_limited` (`:142-145`). ## What is built

1. **Migration 0032**: `participation_profiles` (an organization's participation route, `org_id` references `volunteer_orgs.id`) and `participation_opportunities` (dated or rolling listings, `org_id` likewise). Every served field is a column a person writes, checked in SQL to the validator's shape; `verified_by` and `verified_at` together or not at all; a trigger raises `revision` on every change and **clears the verification when content changes without a new `verified_at`**, so a verification always covers exactly what is served; timezone and venue-date consistency are checked by the same trigger. Three service-role-only read functions do the serving filter in SQL. RLS on, no policy, client roles revoked. **No API route writes.** Bundle, verify query, tested back-out.
2. **`lib/participation.js`**: query parsing, area resolution, projection to the client shape, filters, pagination. **Three routes**: `app/api/explore/organizations`, `app/api/opportunities`, `app/api/opportunities/detail`.
3. **Flag** `participation` and a per-identity limiter `participationLimiter`.
4. **The listing template** for a person: `YOUR_TODO.md` 2.23.

## Rulings (all proposed, Vibhav to confirm)

- **P1, flag and session.** Off: all three answer the non-retryable 503 `feature_unavailable`, nothing read. Session required (`requireUser`; the contract's Public "No"); the answer is the same for every household and reads no household table; `X-Halo-Home-Context` ignored. Limiter `participationLimiter`, 120 a minute per identity across the three, fail-open (no provider is called; the B12 reasoning), 429 with Retry-After 60. Every answer is `private, no-store` (rows can change at any time).
- **P2, only verified rows are served.** A row is served only when `verified_by` and `verified_at` are set and `verified_at` is not in the future. Searches also need freshness: an opportunity verified within the last 29 days (the client hides a listing checked more than 30 days ago, `explore-opportunities.ts:81`; one day of margin so a served listing is not hidden a moment later), an organization profile within 180 days.
- **P3, upcoming means not yet started.** `opportunities.search` serves only `status = 'listed'`, and a scheduled listing only while `starts_at` is after now (A01-A03 acceptance: "Scheduled events disappear from primary discovery at start"). Rolling programs are `kind: 'rolling'`, never given dates, and stay only while their verification is fresh. Cancelled, full, postponed, started and expired listings are never in a search.
- **P4, `opportunities.detail`** (`?id=`): the bare `CommunityOpportunity` plus `revision`, for any verified listing whatever its status, date or freshness, so a saved commitment can learn it was cancelled or has passed; the client labels it (`opportunityState`). Unknown and unverified are the same 404. No consumer exists yet, so the shape is ours to confirm.
- **P5, area, no proximity.** A listing carries `served_place_ids`, gazetteer ids from `locations.search` (`us-county:`, `us-place:`, `us-zcta:`) or `us-state:NC`. It is shown for an area when that set holds the area's own id, the county containing the area's Census internal point, or `us-state:NC`. Never a distance, radius, travel time or "near you". Only the area `id` is read (B05 D8); an id outside the gazetteer is treated as no area.
- **P6, availability.** No area, or no servable listing serving it: `no_coverage`. Servable listings exist for the area but the interest, search or timing filter removes them all: `empty`. Otherwise `ready`. `partial` only when a stored row fails the client's own validator and is withheld (the SQL checks make this a should-not-happen). `unavailable` is never a 200: an unreadable directory is a 5xx (a missing migration 503, anything else 500).
- **P7, `complete` is always `false`.** Its meaning is "HALO's directory holds every opportunity in this area", which a hand-verified directory can never claim, and the screen would say "This result set is complete." Rejected alternative: `nextCursor === null` (true only of HALO's own rows). Organizations: also `false`.
- **P8, top-level `checkedAt`**: the oldest verification date (UTC `YYYY-MM-DD`) among the area's servable listings, a lower bound for "Sources checked"; `''` when there are none. Each item's `checkedAt` is its own verification date.
- **P9, query.** `interest` is `All interests` or one of the four; `timing` is `all`, `upcoming` or `rolling` (organizations take no `timing`); `search` at most 160 characters, every word must appear in the fixture's fields; `area` is JSON with an `id`, or absent. Anything else is a 400. Unknown keys are ignored. 20 items a page; `cursor` is opaque, bound to the query, and a cursor from another query is a 400. Order: scheduled by start then id, then rolling by title then id; organizations by title then id.
- **P10, organization profiles.** One profile is one participation route of one `volunteer_orgs` row; an organization may have several. `scopes` is `[]` (the screen ignores it with a runtime, `ExploreOpportunities.tsx:56`). A profile `address` needs `address_kind` (`office`, `mailing`, `meeting` or `service-area`, not served) and a written `address_role` sentence saying what the address is; an opportunity's address column is `meeting_address` and holds a meeting place only, never an office or mailing address.
- **P11, writing.** Only a person in the SQL editor (`YOUR_TODO.md` 2.23). No route, job or script inserts content. `volunteer_orgs.last_verified` is not used: it is the organization's own check and stays as it is.

## What a person must write per listing

Every listing: `id` (lowercase slug, unique), `org_id` (the `volunteer_orgs` row), `served_place_ids`, the official `url` (https), `verified_by` (who checked, a name or initials) and `verified_at` (when, normally `now()`), each text field a plain sentence with no em dash.

- **Organization profile:** `title`, `organizer`, `interest` (`Cleanup`, `Trees & habitat`, `Gardening` or `Community learning`), `area` (the served area in words), `mission`, `work`, `source_title` (the link's label), `effort`, `age`, `cost`, `access`, `bring`, `followup`, `steps` (1 to 30 `{title, text}`); optional `extra_sources` (up to 20 `{title, url}`), `address` with `address_kind` and `address_role`, `contact`.
- **Opportunity:** `title`, `organizer`, `interest`, `artwork` (`tree`, `cleanup` or `garden`, an illustration, never the venue), `kind`; for `scheduled` `starts_at` and `ends_at` (with zone) and for `rolling` neither; `time_label` (as the person reads it, venue local), `status` (`listed`; `cancelled`, `full` or `postponed` only when the organizer says so), `area`, `venue` (the meeting place), optional `meeting_address` (the meeting place's address only), optional `venue_timezone` with `venue_timezone_basis` (`source` when the listing states it) and `venue_local_date`, `summary`, `work` (1 to 20 short tasks), `duration`, `cost`, `age`, `access`, `bring`, `join_text` (the official next step), `safety`. "Not stated" is a valid answer for cost, age or access: write that, never a guess. There is no capacity, distance or availability column on purpose.

## Dropped or blocked, and why

- Listing content: not written. Who writes and verifies it, and for which organizations, is B05 open question 7, still open.
- Refresh as a source revalidation job, crawling, event APIs, geocoding, radius and distance: none (A01-A03 "Refresh listings"); the screen's refresh re-reads.
- Outdated-listing reports, participation records and changed-event review: their own packages.
- The frontend lane: `OrganizationResults` has no `availability`, so "no verified organizations here" and "no match" look alike (an error already differs); the coverage sentence prints an empty `checkedAt` as "Sources checked ."; `opportunities.detail` has no consumer.
