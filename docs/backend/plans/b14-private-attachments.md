## What is built

1. **Migration 0028** (`supabase/migrations/0028_household_attachments.sql`): `household_attachments` (one row per processed file: owner, collection, record id, revision, name, type, size, pixels, object path, linked flag), `attachment_object_sweep` (storage paths to delete), both RLS on with no policy and client roles revoked; functions to read, reserve, commit an upload, remove, check references, count, expire staged uploads and list/forget due objects; triggers that link references on a workspace write, delete a record's files with it, queue every deleted file's object, delete all files on a clear all, and freeze a settled `attachments` ledger row. A guarded block creates the private bucket `household-attachments` when the `storage` schema exists.
2. **`lib/attachmentImage.js`**: signature sniffing and `sharp` re-encoding (Ruling A2, A4).
3. **`lib/attachmentStore.js`**: RPC wrappers, storage I/O through the service role client, the sweep, the reconcile body.
4. **Routes**: `app/api/attachments/route.js` (upload), `inspect/route.js`, `download/route.js`, `remove/route.js`; an `attachments` overlay in `app/api/operations/route.js`.
5. **Workspace**: W4 lifted when the flag is on (Ruling A7); `pendingOperations` lists unresolved `attachments` operations too.
6. **Privacy**: the table in `lib/privacyInventory.js`, its counts merged into clear-all counts, the clear route sweeping the household's objects after a clear all, and the daily cron sweeping everything due.
7. **Flag** `attachments` (`HALO_FEATURE_ATTACHMENTS`), off by default, and it needs `workspace` on too.

## Rulings

- **A1, flag and retention (proposed, Vibhav to confirm).** Off by default. A file is kept until the person removes it, removes or edits its record so it no longer references it, clears all, or deletes the account. An upload not linked to a saved record (a staged observation or note photo) expires after 24 hours.
- **A2, types (proposed, Vibhav to confirm).** JPEG, PNG and WebP only, decided by the file's signature and by `sharp`'s own decoder, never by the name or the declared type. HEIC is refused: this `sharp` build's HEIF decoder reads AVIF only. **PDF lab reports are refused** (422): a PDF cannot be re-encoded here, so its metadata cannot be proven gone. The report screen offers PDF; it will show the generic "Check the highlighted information" sentence.
- **A3, limits (proposed, Vibhav to confirm).** 10 MiB per file as received (the contract's UI limit), at most 40 megapixels, at most 15 MiB after processing; 20 files per record; 200 files and 500 MiB per household; 30 uploads per household per hour (fail-open, like privacy). **Vercel refuses request bodies over 4.5 MB before the route runs** (413), so that is the real upload limit in production; the screen then says the service is unavailable and nothing is recorded.
- **A4, synchronous processing (proposed, Vibhav to confirm).** Every upload is decoded and re-encoded server side to the same format (orientation applied, sRGB, no EXIF, GPS, XMP, IPTC or ICC), and the output is decoded again to prove no metadata survived. There is no malware scanner; re-encoding from decoded pixels is the content check. So `status` is always `ready` and `quarantined`/`rejected` are never produced. An undecodable file is a 422 before any claim; nothing is recorded or stored.
- **A5, reports are stripped too.** The report screen sends `metadataRemoved: false` (reports "may retain document metadata"); the server strips them anyway and answers `metadataRemoved: true`.
- **A6, unavailable answers (proposed, Vibhav to confirm).** Flag off or 0028 missing: upload **403** `feature_unavailable` (a 5xx would make the client lock on an operation that was never recorded); remove a 200 `failed` receipt with `changes: {}` (the W1 pattern); inspect, download and the `attachments` reconcile the non-retryable 503.
- **A7, linking.** A report upload names an existing test of the household (else 422) and is linked at once: the test record gains the file's descriptor and its revision goes up by one, in the upload's transaction. An observation or note photo is staged under the client's stable record id and linked by the acknowledged workspace write that references it. A workspace write may reference only a ready file of this household staged or linked for that same collection and record id, at its exact revision (else `invalid_reference`); the stored reference is rewritten to the file's canonical descriptor. A write that drops a linked reference deletes that file; removing a record deletes its files. With the flag off, W4 stands.
- **A8, removal.** Exact revision (`If-Match` must equal it). The file row goes, the record loses its reference (revision + 1), entered results stay, and the receipt carries the canonical rows of the file's collection (never empty `changes` on success). Another household's id is "not found", identical to a missing one.
- **A9, objects.** Path `<profile id>/<attachment id>`, built in SQL from the verified owner and a server uuid. Only the service role reads or writes the bucket; no storage policy exists. A trigger queues the object of every deleted row (remove, record delete, dropped reference, clear all, account deletion cascade, staged expiry) in `attachment_object_sweep`; each upload reserves its path there first (due in one hour) and the commit clears it, so a crash between storage and the database still ends in deletion. The queue is drained by the remove route at once, by the privacy clear route after a clear all, and by `/api/cron/daily` (bounded, never fatal). An object whose row still exists is never deleted.
- **A10, download.** Streamed bytes, the stored type, `Cache-Control: private, no-store`, `nosniff`, a sandbox CSP and a generic file name. The revision must match (409 otherwise).
- **A11, ledger.** Domain `attachments`, kinds `attachments.upload` and `attachments.remove`. Receipts hold the attachment id, collection names and a reason code only, never a file name. A settled `attachments` row may not change status (the 0026 guard's pattern). The reconcile answers a succeeded upload with the file's current descriptor and the current rows of the collections it touched, every other status with `changes: {}`.
- **A12, export (proposed, Vibhav to confirm).** Metadata only, never bytes: collection, record id, revision, type, size, pixels and dates in the base tier, the file name as private text; tests and observations in `home`, notes in `explore`. The object path and operation id are withheld. Clear Journal keeps the table; clear all deletes it.
