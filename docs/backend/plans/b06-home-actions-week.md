## What this package is, and what it deliberately leaves out

Four registry operations drive My Week (`/app`, `/plan`), which today shows "Your tasks could not load. Reconnect and try again." (F: `ExpandedPreviewState.tsx:77`) and cannot add a task. No route exists for any of them on either side (digest 0).

**In scope:**

- `actions.load`, GET `/api/frontend/actions`, and `actions.commit`, POST `/api/frontend/actions/commands` (F: `runtime.ts:29-30`). These two alone make My Week load and accept a new task: the workspace `scenario` that gates `mutate` starts `ready` and is not a settings dependency (digest 6.2). They come first.
- `week.changes`, GET `/api/week/changes`, answering only the honest empty body (H4), and `week.acknowledge`, POST `/api/week/changes/acknowledge`, which validates and refuses (H4).
- Migration **0023**: three tables plus a read function and the atomic commit function (H6, H8, H9, H10).
- `GET /api/operations` for domain `actions` returns a current snapshot rather than a stored one (H3, H18), because the reconcile path validates `snapshot` (F: `adapters.ts:7,11`).
- Capability flag `tasks`, off by default (H1, H17).

**Dropped, with reasons:**

- **The `clear` command kind.** No production sender: `eraseActions` returns `false` whenever a service is injected (F: `ExpandedPreviewState.tsx:153`), the review adapter refuses it (F: `action-service.ts:71`), and clearing tasks belongs to `privacy.clear` (F: `settings-preview.ts:36`). Refused with a 400 (H14). *Unblocked by:* a sender and a ruled scope.
- **`reminderStates`.** Read-only scheduler evidence (F: `week-reminders.ts:5`), and no scheduler exists (HO-072, spec:177). Omitted, which is valid (F: `test/frontend-week-reminders.test.mjs:12-15`). The meta `reminder` boolean is stored as sent and claims nothing (C7).
- **Occurrence tables.** Recurrence is client-driven, a new task keyed `<base>:occurrence:<date>` (F: `MyWeekWorkspace.tsx:126`); `plan_occurrences` (BE-131, spec:564) is not required by this contract (digest 7.6).
- **Acknowledgement storage.** Nothing can be acknowledged that was never emitted (A5 reading 1, H19).

**Blocked, not planned:**

- **Enabling tasks for real households.** Tasks are free text a person typed (title, `note` up to 3,000 characters, an unbounded `history`), plus `outdoorPlan.place` and household group text in notes (digest 9.3, C2). BE-320: "Publish actual configured retention periods before collecting new private data." (spec:872). *Unblocked by:* Vibhav's retention periods (STATE decision 3, Open question 1), then the flag.
- **`week.changes` with content.** No change source exists: organizer events (MP-121 spec:2752, BE-261 spec:768) have no route, `forecast.read` is unbuilt, the `tests`/`assets` collections have no storage, and water alerts are linked to no task (digest 6.1, C4). *Unblocked by:* any one of those sources, a ruling on what each `kind` means for it, then the acknowledgement table and A7.
- **`portableTasks` and carry-forward on a home move** (F: `account-service.ts:6`; BE-206 spec:698). Needs Open question 2.
- **Export and deletion of tasks under `privacy.*`** (B12). Until then deletion is the profile cascade, which 0023 provides.

## Rulings made in planning (H8 and up)

- **H8, the effect and the ledger settle commit in one transaction.** The commit function (0023) ends by updating this operation's own ledger row, `where operation_id = $op and profile_id = $owner and domain = 'actions' and status = 'pending'`, to `succeeded` with the minimal receipt; if no row matches it raises `HALO_OPERATION_NOT_PENDING` and the whole call rolls back. So a task write exists if and only if its operation is `succeeded`. That closes C9 and digest 4.6 item 4: today effect and settle are separate statements (W: `lib/operations.js:166-172`), so a process dying between them leaves a committed task under a row the reaper will settle `failed`, and the client then says "No save was applied. Your draft is kept for review." (F: `ExpandedPreviewState.tsx:114`), which would be false. Under H8 that sentence is always true. It is race-safe against the reaper because both are conditional updates on `status = 'pending'`: whichever commits first wins and the other finds nothing (the reaper's own reasoning, branch `worktree-agent-adee2e4acf9ddd3f3`, `reapAbandonedOperations`). `runOperation`'s own settle afterwards rewrites the same minimal receipt with `operationId` added, which is harmless. No B06 task edits `lib/operations.js`.
- **H9, one SQL read function builds every snapshot.** `read_household_actions(p_profile_id)` returns `{version, actions, metas, preferences}` as one `jsonb` value in one statement, used by the load, by the commit function's return value, by a replay and by reconcile. Three reasons. It is one consistent snapshot. A function's scalar result is not subject to PostgREST's `max_rows` (Supabase's default is 1,000), so a household over 1,000 tasks is not silently truncated (finding F1; the frontend's own volume fixture is 500 tasks, F: `production-large-week.spec.ts:8-10`). And the action object shape is fixed in one place: exactly `{id, key, title, reason, origin, date, state, revision}`, `date` as `''` for a null `due_date` (formatted with `to_char(..., 'YYYY-MM-DD')`, never through `DateStyle`), so the add-of-an-existing-key check `sameValue(action, old)` (F: `action-service.ts:109`) compares identical key sets on every read. `version` is internal and stripped before anything is emitted.
- **H10, compute in JS, validate the whole result, commit against a household version, retry a lost race.** Per-action revisions cannot protect metadata, because a meta changes without its action's revision moving (the reference adapter never bumps it, F: `action-service.ts:72-81`, and the weekly planner sends metas for tasks not in `changes`, F: `WeekReviewPlanner.tsx:17`). Two concurrent commits could each validate a pair (new date, old meta) and (old date, new meta) and together store a pair neither validated, which is trap T5 by another route (finding F5). So 0023 keeps one internal counter per household, `household_action_state.version`. The route reads the snapshot with its version, applies the command in JS (H15), validates the entire resulting snapshot with the client's rules, then calls the commit function with that base version; the function advances the version only `where version = p_base_version` and otherwise raises `HALO_STALE_BASE`. On `HALO_STALE_BASE` the route recomputes from a fresh read, at most three attempts, re-evaluating the client's own preconditions each time so a retry never weakens them; after the third it refuses with reason `busy`. The version is never emitted and is not a contract field; it exists only to make "validate the whole resulting snapshot before commit" (H7) literally true.
- **H11, the refusal taxonomy.**
  - A request that is malformed without reading any state (shape, types, bounds, unknown keys, `clear`, duplicate seed keys, duplicate change ids, an unparseable signature, an unstorable value per H13) is a **400** with field errors, decided before the ledger claim, so nothing is recorded.
  - A request refused because of stored state (stale revision, changed metadata, unknown action, an invalid resulting snapshot, `busy`) is a **200 receipt** `{operationId, status: 'failed', reason, message}`, stored in the ledger as `{status: 'failed', reason}` plus, for `stale_revision`, the current `[{id, revision}]`. This is the contract's own refusal shape (F: `action-service.ts:19`, digest 5.3), and HO-118 allows "a documented precondition response for stale revisions" (spec:267). `message` is derived from `reason` at response time and shown verbatim (F: `ExpandedPreviewState.tsx:93`).
  - A replay of the route's own refusal answers the same 200 receipt again.
  - A replay that meets a settled `failed` row the route did not itself refuse, in **either** shape (result `null` from an in-process throw, W: `lib/operations.js:168`; or the reaper's `{status: 'failed', reason: 'abandoned'}`), is a terminal **409** with `reason: 'abandoned'` or `'not_applied'` (H7; B05 D9 precedent).
  - A replay that meets a `pending` or `unknown` row is the house **503** "still being processed", retryable (W: `app/api/luna/conversations/clear/route.js:126-133`).
  - A body over the cap is **413** (W: `lib/validate.js:319-329`), which the client maps to `failed`, not a lock (F: `runtime.ts:144`).
- **H12, `expectedMetadata` is parsed and deep-compared, all keys first** (digest A3, T6). Each value is `JSON.parse`d (unparseable is a 400) and compared with the client's own `sameValue` (F: `action-service.ts:102`) against the stored meta, or `null` when the key has none. Byte comparison is rejected because `jsonb` reorders keys, so the second edit of any task would always refuse. Every expected key is checked before anything else, and one mismatch refuses the whole command with reason `metadata_changed`, nothing changed, preferences included (F: `action-service.ts:58`; F: `EXPANDED_PRODUCTION_INTEGRATION.md:29`).
- **H13, exact echo, and only storable values** (T4). Titles are stored `trim()`med with JavaScript's own `trim` (F: `action-service.ts:109`). A sent meta is stored verbatim as `jsonb`, unknown keys included, because coverage compares key counts (F: `action-service.ts:102,112`). Seed fields other than `key`, `title`, `reason`, `origin` are ignored and never stored, because seeds are spread from caller objects (`{ ...draft.seed, title: draft.title }`, F: `ExpandedPreviewState.tsx:143`); `seed.date` is ignored in favour of `command.date` (C6). Three server-only refusals (400), each because the value cannot round-trip and would turn a real success into "The save outcome is not confirmed." (finding F2): a string anywhere in a stored value containing U+0000 or a lone surrogate (`jsonb` rejects both); a non-finite number (a JSON `1e400` parses to `Infinity`, which supabase-js serializes as `null`); a `date` or `completedOn` in year 0000, which `validActionDate` accepts (F: `expanded-preview.ts:30-35`) and a Postgres `date` cannot hold. Every value the client UI can produce is still accepted.
- **H14, command kinds.** `add`, `revise` and `delete` only; `clear` is a 400 (digest A6). `revise` with `changes: []` is valid and is the preferences write (T3; F: `production-home-account.spec.ts:27`). `delete` of an id the caller has no row for, never existed or another household's, is an idempotent `succeeded` with nothing written (BE-200 spec:685), identical for both cases so it is no existence oracle; the reference refuses instead, but coverage accepts it (F: `action-service.ts:107`). `add` of a key already present is a true no-op for that seed: the action comes back unchanged, revision included, and every metadata entry for that key, `null` included, is ignored (F: `action-service.ts:63,79,109,111`; F: `EXPANDED_PRODUCTION_INTEGRATION.md:31`). `initialStates` is accepted on every kind, because the edit-task path sends it on `revise` (digest 2.2.1, finding F6), and applied only on `add`. Duplicate seed keys in one batch are a 400 (the reference keeps the first, then coverage fails the second).
- **H15, the server runs the client's own rules, transcribed.** `lib/actionRules.js` holds a JavaScript transcription, types stripped and nothing improved, of `validActionDate` and `actionDraftError` (F: `expanded-preview.ts:30-40`), `revisedActionBatch` (F: `expanded-preview.ts:44-48`), `eventInstant` (F: `week-preview.ts:11-17`), `object`, `text`, `validZone`, `actionMetadataError`, `validActionPreferences`, `validActionSnapshot`, `sameValue` (F: `action-service.ts:27-36,38-53,86-99,102`), each with its line range in a comment. A sent meta is validated unmerged, as the reference does (F: `action-service.ts:77`); the resulting snapshot is validated merged with `emptyWeekMeta`, as the load does (F: `action-service.ts:96`). The order is the reference's: signatures, then kind, then metadata, then preferences (F: `action-service.ts:58-82`). Node's ICU and the browser's can still disagree on a zone (digest 9.5); that residual is recorded, not solved.
- **H16, `unresolvedOperations`** (T1, T2, T8). Always present on a load and on every succeeded receipt, including a replay and a reconcile, because the production adapter requires the array (F: `adapters.ts:7,9`; C8). Built from `listUnresolvedOperations` for the one domain (`actions`, or `week-updates`), **after** the commit function returns (when H8 has already settled the row), with the caller's own operation id filtered out explicitly as well, then the first 100 ids, oldest first (F: `action-service.ts:90`). Never called inside `execute`, which is the account bug (C1).
- **H17, the capability flag `tasks`** (`HALO_FEATURE_TASKS` in `lib/features.js`, added to `SCRUBBED_ENV` in `test/helpers/sandbox.mjs`). Off: `actions.load` is a non-retryable 503 `feature_unavailable` with no read at all (the Luna precedent, W: `app/api/luna/conversations/clear/route.js:175`), so My Week stays as dead as it is today rather than showing an empty week that may be false. `actions.commit` is a 200 `{operationId, status: 'failed', message: <disabled reason>}` with no ledger row and no read (the account precedent, W: `app/api/account/commands/route.js:687-691`), because a 5xx on a mutation would lock the surface (F: `runtime.ts:144`). `operations.read` for a succeeded `actions` row is a 503 while off. The week routes are not gated: they collect no free text.
- **H18, reconcile of an `actions` operation returns the current snapshot** (digest A2 reading 2, A8 reading 2; follows from H3). `app/api/operations/route.js` gains one domain hook: for `domain = 'actions'` and status `succeeded` it adds `snapshot` from H9 plus H16's list, excluding the operation being read. A current snapshot cannot roll back another device's later change the way a frozen one would (A8), and the client's reconcile checks validity, not coverage (F: `ExpandedPreviewState.tsx:113`). Every other domain's replay stays verbatim.
- **H19, `week.acknowledge` always refuses, through the ledger.** A valid body is claimed in domain `week-updates` (kind `week.acknowledge`) and settled as `{status: 'failed', reason: 'unknown_change'}`: no change has ever been issued, so every `(id, version)` is unknown. No task table is read, so a real action id and a foreign one answer identically. The response is 200 `{operationId, status: 'failed', reason: 'unknown_change', message}`; the client shows its own "The update was not applied. You can try again." and clears its lock (F: `WeekUpdates.tsx:23`). Recording the refusal is what lets a timed-out acknowledgement reconcile to `failed` instead of a 404 lock (digest 4.6 item 5). It never answers `succeeded`, so the missing-`acknowledged` trap (T11) cannot arise. A7 is recorded for the future: when a source lands, the server excludes acknowledged versions from `week.changes` and returns the full `id:version` set (T10).
- **H20, `week.changes` lists genuinely unresolved `week-updates` operations** (digest 6, row 3), so the H4 body is what every household gets except during an acknowledgement in flight. It reads no other table and needs only 0017.
- **H21, transport.** On both POSTs, `Idempotency-Key` is required, must be a UUID, and must equal the body's `operationId` after trim and lowercase (T12; the house check, W: `app/api/account/commands/route.js:673-683`, made mandatory as B05 D9 did). `If-Match` is a 400 `precondition_unsupported`: there is no snapshot revision to match and the client never sends one (F: `adapters.ts:10`). `X-Halo-Home-Context` is ignored (H2). `export const maxDuration = 60` on all four routes (H7; Next.js 16 segment config, `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/02-route-segment-config/maxDuration.md`), stated in the route as below the 120 s stale window (W: `lib/operations.js:61`), so a live commit is never reaped. Commit body cap 4,000,000 bytes, under the platform's 4.5 MB request limit, sized for the weekly planner, which sends every meta and a signature for every key (F: `WeekReviewPlanner.tsx:17`); acknowledge cap 2,048 bytes.
- **H22, copy.** Every server-authored string (refusal messages, the disabled reason, error envelopes) is in one frozen table and contains no U+2014 (AGENTS.md; T13). Text a person typed is echoed exactly and never rewritten, because coverage compares it (F: `action-service.ts:109`); AGENTS.md binds app copy, not user content.
- **H23, no field caps the contract does not set.** `reason`, `origin`, `key` and `meta.history` have no contract bound (digest 7.1, 7.2); the server adds none beyond non-empty `key` and the body cap, because any cap must still accept every current caller (digest 7.1) and a cap on `history` would brick a task once reached. Database length checks on `title` and `note` are backstops that use `char_length` (code points), which is never tighter than the client's UTF-16 `length` (finding F3). The unbounded history is Open question 5.
- **H24, the load never hides a stored row.** If the server's own `validActionSnapshot` rejects a stored snapshot (only possible through ICU drift, digest 9.5), the load logs the offending action id and the validator's message, never its content, and returns the snapshot unchanged. Silently omitting the row would tell the person a task does not exist.

Further findings from planning:

- **F1:** a plain PostgREST select of tasks truncates at `max_rows` (1,000 by default) with no error. Avoided by H9.
- **F2:** three values pass the client and cannot round-trip through storage: U+0000 or a lone surrogate in `jsonb`, a non-finite number through supabase-js, year 0000 in a Postgres `date`. Refused by H13.
- **F3:** the client measures `title` and `note` in UTF-16 units, Postgres in code points. Database checks are backstops only (H23).
- **F4:** a 409 or `failed` on commit does not reload (digest 1.4), so the person's snapshot stays stale until a page reload; refusal messages say to reload. Flag to Yogi.
- **F5:** metadata changes do not advance any revision, so per-action revisions cannot serialize concurrent commits. Hence H10.
- **F6:** the edit-task path sends `initialStates` on `revise` (digest 2.2.1). Hence H14.
- **F7:** a reconcile of a request that never arrived is a 404, which the client keeps as a lock until reload (digest 4.6 item 5). Client-side; flag to Yogi.

Checks, each added idempotently (0022 pattern): `state in ('saved','waiting','completed')`; `revision >= 1`; `char_length(title) between 1 and 160` and `char_length(action_key) >= 1` (backstops, H23); `meta is null or jsonb_typeof(meta) = 'object'`; `pref_key in ('week:focus','food-interests','week:availability','week:season-dismissals','week:review-preferences','outdoorPlan')` and `value <> 'null'::jsonb` (no key can be deleted, digest 2.2.3); `version >= 1`. Index on `household_actions (profile_id, created_at, id)`.

`public.read_household_actions(p_profile_id uuid) returns jsonb` (stable), per H9: `{version, actions, metas, preferences}`, `version` 0 when there is no state row, actions ordered by `created_at, id`, `metas` only for non-null `meta`.

`public.commit_household_actions(p_profile_id uuid, p_operation_id uuid, p_base_version bigint, p_writes jsonb) returns jsonb`, one transaction:

1. Advance the version: insert version 1 when `p_base_version = 0`, else update `where version = p_base_version`; no row affected (or a unique violation on the first insert) raises `HALO_STALE_BASE`.
2. Apply `p_writes`: deletes by id, updates (title, date, state with `revision = revision + 1` for changed actions; `meta` set or cleared without touching `revision`), inserts (revision 1), preference upserts. Every statement is `where profile_id = p_profile_id`; a short row count raises `HALO_STALE_BASE` (defensive; cannot happen under step 1).
3. Settle the ledger per H8 with `{status: 'succeeded', affected: [{id, revision}], removed: [id]}`, else raise `HALO_OPERATION_NOT_PENDING`.
4. Return `{receipt, snapshot: read_household_actions(p_profile_id)}`.

Refusals are SQLSTATE P0001 with the code as the message, read by a helper modelled on `haloRefusal` (W: `lib/homeContextRpc.js:136`); `HALO_INVALID_INPUT` for a malformed `p_writes`. Unavailable is PGRST202, 42883, PGRST205 or 42P01 (W: `lib/homeContextRpc.js:42`).
