# B08 Evidence (daily maxima and `evidence.read`): implementation plan

Spec: `docs/product/ai/HALO_BACKEND_WORKING_SPEC.md` on `origin/codex/october15-review-refinement`, sha256 `fc1fec4b180dc5057b2edf1c2203143d85535b43364502e674d34e04d415be86`, 521,027 bytes (re-verified 2026-10-19 for this plan). Citations: `S:` is that spec, `W:` this tree (the frontend is merged in at `1253025`, frontend ref `5ac06f6`, so frontend files are cited in the tree), `D:` the B04 contract digest, `.superpowers/sdd/b04-settings-alerts-evidence/contract-digest.md`, binding where it quotes the frontend.

**The decision.** On 2026-10-19 Vibhav decided that the daily pipeline records each day's maximum (STATE decision 1, W: `docs/backend/STATE.md:125-126`). This plan turns that into a recording pipeline that starts accumulating data first, then a read route the client's validator accepts truthfully. Days before recording starts have no daily maximum and are reported as missing, never backfilled and never labelled from app-time readings.

Primary requirements, each **partial** unless the checkpoint shows otherwise: **HO-100** (S:232) as narrowed by the B04 tracker row to `evidence.read` (W: `docs/backend/requirements-tracker.md:299`); **MP-347** (S:2301, aggregation basis stated, incompatible series not pooled); **DS-039** (S:1084, history basis metadata, DST offsets, backfill not merged invisibly with current snapshots); **BE-092** (S:500, measured versus modelled preserved); **DS-031 to DS-034** (S:1068-1074, AirNow station versus reporting area, shared requests, source-budget review); **DS-036 to DS-038** (S:1078-1082, Open-Meteo labelling, `generationtime_ms` is not an issue time); **HO-053**, **AC-131**, **UI-109** (S:2309, 2313, 2305, Patterns), **HO-054**, **UI-110** (S:2336, 2332, Season); **HO-019**, **HO-020** (S:1415, 1440, station versus area, hourly gaps); **HO-089** (S:211, carry source and method into historical records). Gating, not closed: **BE-320**, **BE-322** (S:872, 877, retention). Release gates: none closed by this package.

## What this package is, and what it deliberately leaves out

`evidence.read` is `GET /api/evidence` (W: `lib/frontend/production/runtime.ts:73`), called by `useProductionHistory` with `{kind:'history',from,to}` (W: `components/production/WeekSources.tsx:6`) from two screens: Patterns, a fixed 84-day window (W: `components/expanded/WeekEvidence.tsx:31`), and Season, a whole meteorological season clamped at today (W: `WeekEvidence.tsx:43`; D: 1.6). The validator (W: `WeekSources.tsx:8`, quoted in D: 2.4) accepts only `comparison.basis === 'daily maximum'` and `comparison.context === runtime.homeContextId`. No route exists today, so both screens show "Environmental history is unavailable." (W: `lib/frontend/week-evidence-preview.ts:11`).

**In scope:**

- Migration **0025**: the `daily_maxima` table, a one-row recorder state table, an upsert function with a finality guard, and a schema probe.
- A daily recorder, `GET|POST /api/cron/daily-maxima`, that fetches each completed day's hourly series and stores its maximum per home context and factor. **It ships first**, because data only accumulates from the day it runs.
- `GET /api/evidence`, answering from `daily_maxima` only.
- `GET /api/profile` gains the additive `home_context` the frontend already expects (E20), without which the context check fails for every real household.
- Contracts, a conformance suite that runs the client's own consumption code, the tracker and the checkpoint.

**Dropped, with reasons:**

- **Serving `daily_scores` through `evidence.read` in any form.** Those rows are app-time observations collapsed by `latestPerDay` (W: `lib/journalHistory.js:112-120`, `app/api/history/route.js:101`). Labelling them `daily maximum` is the false provenance claim the decision exists to avoid (D: 10).
- **Importing the onboarding backfill** (W: `lib/backfill.js:63-110`), although its rows are tagged `aqi_basis: 'daily_peak_modeled'` (W: `lib/backfill.js:103`) and the spec calls them "Backfilled daily maxima" (S:2301). See E9 and Open question 6.
- **`nextCursor` and paging.** No caller reads or sends a cursor (D: 1.6). Never emitted.
- **Pollen and Outdoor mold values.** Always `value: null` with a reason (E7).

**Blocked, not planned:**

- **A purge of environmental history.** Retention for environmental history is undecided (W: `docs/backend/STATE.md:129-133`). Nothing is purged and no period is invented (Open question 1).
- **Pollen as a series.** Needs a source with an intraday or daily-maximum series and storage rights (S:1042 DS-015, S:1467 HO-021). *Unblocked by:* such a source, Vibhav's call, then a new method version.

## What "the day's maximum" can honestly mean with the data HALO fetches

What the pipeline fetches today, per household, at the moment it runs:

| Factor | Today's fetch (W) | What it is | Is there an hourly series for a past day? |
| --- | --- | --- | --- |
| Air, measured | AirNow `observation/latLong/current`, `distance=25` (`lib/dailyReadings.js:145-150`) | The reporting area's **current** hour, not a station, not a day (S:1068 DS-031) | **Yes**: AirNow `aq/data` by bounding box returns one row per site, pollutant and UTC hour; HALO already calls it for the map (`lib/mapLayers.js:144-154`, `:85-110`) |
| Air, modeled | Open-Meteo `current=us_aqi` (`lib/dailyReadings.js:156-166`) | One modeled instant | **Yes**: `hourly=us_aqi&past_days=N`, already used by the backfill (`lib/backfill.js:120-131`) |
| UV | Open-Meteo `current=uv_index`, plus `hourly` for today only (`lib/dailyReadings.js:170-178`) | One modeled instant; `uvPeakWindow` takes today's hourly max (`:58-81`) | **Yes**: `hourly=uv_index&past_days=N` |
| UV fallback | OpenUV, 45 a day globally (`lib/dailyReadings.js:182-194`, `lib/ratelimit.js:15-19`) | One instant | No. Never an input |
| Pollen | Google Pollen `forecast:lookup&days=1`, `dailyInfo[0]` (`lib/dailyReadings.js:197-207`, `:83-96`) | **One daily forecast index per type**, no intraday values | No history endpoint (`lib/backfill.js:7-9`), and storage is limited by terms (S:1042 DS-015) |
| Outdoor mold | NWS hourly forecast, first period's humidity and rain chance (`lib/dailyReadings.js:209-216`, `:98-115`) | A **proxy estimate** HALO computes, a three-word category (`lib/dailyPayload.js:135-136`, D: 8.4) | Not a measurement of anything; the frontend itself has "No compatible historical mold series" (`week-evidence-preview.ts:33`) |
| Water, radon, lead | Quarterly UCMR, a static zone, a static inventory | Not daily | Not `HistoryFactor`s at all (`week-evidence-preview.ts:6`) |

So, precisely:

- **Measurable as a daily maximum: Air and UV only.** Air from the nearest AirNow station's hourly values, or, for a home with no station within 25 miles, Open-Meteo's modeled hourly `us_aqi`. UV from Open-Meteo's modeled hourly `uv_index`. Both are the largest hourly value of one source series over one local day.
- **Not measurable: Pollen and Outdoor mold.** A daily forecast index is not a maximum of anything, and a proxy estimate from one forecast hour is not a measurement. Both are reported unavailable on every date (E7).
- **When:** by a scheduled fetch of the completed day's hourly series, never from the app-time observations seen that day. App-time readings are taken when somebody opens the app (W: `app/api/daily-score/route.js:220-244`) or once by the daily job (W: `lib/backfill.js:317-345`); their maximum is "the largest of the moments HALO happened to look", biased to waking hours, usually one sample (E5).
- **Which day:** the America/New_York calendar date, local midnight to local midnight, 23, 24 or 25 hourly slots (E2). That is the day the household's check-ins use (W: `lib/localDate.js:11`, `lib/frontend/luna-tools-preview.ts:28`) and what the screen calls "Source calendar date" (W: `WeekEvidence.tsx:24`).
- **A day with one observation:** has no daily maximum. One hourly value is 1 of 24 slots, a source gap under E3; one app-time reading is never an input (E6).

## Rulings (E1 and up)

- **E1, a new series, written by a new recorder, read by a new route.** Daily maxima live in `public.daily_maxima` (0025). The recorder never reads `daily_scores`; `GET /api/evidence` never reads `daily_scores`; nothing in `daily_scores` is relabelled or copied. `/api/daily-score`, the daily job's `recordToday` and `/api/history` are unchanged.
- **E2, the day.** `local_date` is the America/New_York calendar date (`HOUSEHOLD_TZ`, W: `lib/localDate.js:11`). The day's slots are the UTC hours whose local date is that date: 24 normally, 23 on the spring-forward date, 25 on the fall-back date. Every row stores `time_zone` and `hours_expected`. AirNow hours arrive in UTC (W: `lib/mapLayers.js:93,103`, `r.UTC`) and are converted with `Intl`; Open-Meteo is requested with `timezone=America/New_York` (the backfill's convention, W: `lib/backfill.js:121-129`) and its local timestamps are matched by date prefix and checked against the expected slot count.
- **E3, the daily maximum.** The largest hourly value of one source series over the slots of E2, at the home context's stored point, computed after the day has ended. For AirNow, a station-hour's AQI is the largest AQI over the pollutants the station reported that hour (EPA's convention, W: `lib/dailyReadings.js:25-37`); sentinel and negative values are dropped (W: `lib/mapLayers.js:89`). **Coverage:** every pollutant the station reported that day must itself have at least `ceil(0.75 * hours_expected)` hourly values (18 of 24, 18 of 23, 19 of 25), else the day is a source gap; for a modeled series the same count applies to the one field. Values: Air an integer AQI, UV rounded to 0.1 (as `uvPeakWindow`, W: `lib/dailyReadings.js:79`). The threshold is Open question 3.
- **E4, settling, and finality.** The recorder looks at each day on up to three runs. On the first run after the day ends, a value is recorded only when every slot is present; on the second and third, coverage per E3 suffices; after the third, a day still short is stored final as `source_gap`, and a day whose provider never answered as `unavailable`. Until then the row is `pending`. A recorded value or a final code is never rewritten, by the upsert's `where missing_code = 'pending'` and by a trigger. Revisions AirNow makes to preliminary data after recording are not chased (known limit, stated in the source label).
- **E5, when.** A separate cron, `/api/cron/daily-maxima`, at `0 12 * * *` UTC (07:00 EST, 08:00 EDT, 7 to 8 hours after the local day ends), processing the three most recent completed days (E4) in **one** AirNow `aq/data` call for the whole window and, per distinct stored point, at most one Open-Meteo forecast call and one air-quality call with `past_days=3`. Separate from `/api/cron/daily` so a slow ArcGIS or household pass (W: `app/api/cron/daily/route.js:18-19,188`) cannot starve it of its 60 seconds, and so a recorder failure cannot cost alerts. If the Vercel plan refuses a second cron entry, the recorder runs as the first step of `/api/cron/daily` with its own deadline (human check, Task 3).
- **E6, one observation is not a maximum.** Follows from E1 and E3. No code path produces a daily maximum from fewer than the E3 coverage, and no app-time reading is ever an input.
- **E7, factors.** `Air` and `UV` are recorded. `Pollen` is never recorded: Google returns one daily forecast index per type (W: `lib/dailyReadings.js:86-95`), so there is no maximum to take; it has no history (W: `lib/backfill.js:7-9`); its storage terms are restricted (S:1042); and the contract's 1 to 3 category (D: 2.4) is not Google's 0 to 5 index, so a mapping would be invented. `Outdoor mold` is never recorded: it is HALO's own proxy from one forecast hour (W: `lib/dailyReadings.js:98-115`). Both are emitted on every date as `value: null` with their reason (E13).
- **E8, one Air source kind per home, fixed by its first recorded day.** `comparison.version` is one string for every factor (E10), so measured and modeled Air would be pooled silently if mixed day by day, against BE-092 (S:500) and MP-347 (S:2301). So: a context is **measured** if, on its first recorded Air day, an AirNow station within 25 miles of its point (the radius of today's reading, W: `lib/dailyReadings.js:147`; haversine, 40.234 km) reported that day; otherwise **modeled**. That kind is read back from the context's latest Air row on every later run and never changes in `daily-max-v1`. A measured context's station gap is a source gap, never a modeled fallback. The station is the nearest one that reported that day; its AQS code is stored as `station_id`. A new station opening near a modeled home needs a new method version. The AirNow call's bounding box is North Carolina padded by 0.5 degrees, not the NC-08 box (W: `lib/mapLayers.js:25`), so a home near the district edge is not misread as unmonitored; a context outside the padded box, or with `state` other than `NC`, is skipped and counted.
- **E9, no backfill, ever, in `daily-max-v1`.** The recorder's state row holds `recording_from`, set by its first successful run to the earliest day that run records and never moved. No day before `recording_from` is recorded, and none before a context's first full day (the local date of `effective_from` plus one, so a move day belongs to neither home). The three-day catch-up of E4 is the same method on the same completed-day series, inside `recording_from`, so it is not a backfill. The 28-day onboarding backfill rows stay in `daily_scores` and are not imported: Vibhav's decision, DS-039's unmet validation of `past_days` "with real historical fixtures before claiming backfill readiness" (S:1084), and a different UV method (`daily=uv_index_max`, W: `lib/backfill.js:129`). Open question 6.
- **E10, `version` is the method version, `daily-max-v1`, on every row and on `comparison`.** The client compares every factor's rows against the one `comparison.version` (W: `week-evidence-preview.ts:43`; `WeekEvidence.tsx:26`), so a per-source version would exclude UV whenever Air's version was chosen. Source differences go in `source` (E17). Any change to E2 to E8 is a new version; old rows keep theirs and the screen marks them "Separate source version, excluded" (W: `WeekEvidence.tsx:27`).
- **E11, `comparison.context` is the server's current home context id.** Read with `readCurrentHomeContext` (W: `lib/homeContextRpc.js:232`), owner-scoped; `X-Halo-Home-Context` is ignored, as B05 D5, B06 H2 and B07 P1 rule. Rows are only that context's. An earlier home's maxima are never served (MP-347 S:2301; the `earlier_home` rule, W: `lib/journalHistory.js:9-16`). A tab whose context id is stale after a move on another device fails the validator with "History could not be verified." (W: `WeekSources.tsx:9`), which is true; no 409 on a read.
- **E12, the second B04 blocker, ruled: a household with no current context gets `{rows: [], comparison: {context: null, basis: 'daily maximum', version: 'daily-max-v1'}, complete: true}`, status 200.** `null` is the only value that passes `=== runtime.homeContextId` for such a client (W: `components/production/ProductionApp.tsx:41`), it is the truth (there is no context), and with `rows: []` it claims no reading. A non-200 would render "This service is unavailable" with a Retry button that can never help (W: `WeekEvidence.tsx:37`). It violates the declared `context:string` (W: `WeekSources.tsx:4`); Yogi is asked to widen it to `string|null` (Task 6). Rows always carry a string `context`. 0016 missing is treated the same way, since the client's id is then null too.
- **E13, one row per date and factor, every date of the range, oldest first.** Factor order `Air`, `UV`, `Pollen`, `Outdoor mold`. The chart's x position is the array index and its caption reads the first and last row (W: `WeekEvidence.tsx:27`; D: 7), so an omitted date would compress the time axis; and the table keys rows by `r.date` within one factor (W: `WeekEvidence.tsx:27`), so a date appears once per factor. A missing value is `value: null` with a `missing` reason from one frozen table, never `0` (D: 7, "Gaps are missing or incompatible readings, not zero.", W: `WeekEvidence.tsx:27`). Precedence for a null row: the factor's own reason (E7); then `Current day is not complete` for today and `Not recorded yet` for a later date; then the window (E14); then `Recorded from <date>. Earlier days have no daily maximum.` before `recording_from` or the context's first full day; then the stored code (`Source gap`, `No reading for this day`, or `Not recorded yet` while `pending` inside the three-day window); then, with no row, `Not recorded yet` inside the window and `No reading for this day` outside it. `Current day is not complete`, `Source gap`, `No reading for this day` and `No compatible historical mold series` are the frontend's own phrases (W: `week-evidence-preview.ts:33`). Pollen's is `Pollen has a daily forecast index, not a daily maximum.`
- **E14, the read window is the latest 84 days.** The screen states "The available environmental series covers at most the latest twelve weeks. Earlier seasonal dates remain missing, not zero." (W: `WeekEvidence.tsx:46`). Until retention is decided and that copy changes, dates before `today - 83` are null rows with `Outside the twelve-week history window`. Stored rows are not deleted (E22).
- **E15, the request.** Query keys exactly `kind`, `from`, `to` (W: `runtime.ts:125-129` sends GET bodies as strings; D: 0); any other key, a missing key, or `kind` other than `history` is a 400 with field errors. `from` and `to` are `YYYY-MM-DD` and must round-trip as calendar dates; `from <= to`; the inclusive span is at most 92 days (the longest season, Spring and Summer, W: `week-evidence-preview.ts:63`). A `to` after the server's today is accepted and its dates are null rows (E13), because the client's today is the same zone and differs only by clock skew.
- **E16, `issued` is `'Unknown'` on every row.** Neither AirNow's hourly data nor Open-Meteo publishes an issue time for these values, and "If a model run time is unavailable, return unknown rather than substituting retrieval time" (S:1082 DS-038). The retrieval instant is stored as `retrieved_at` for audit and never emitted. `'Unknown'` renders as "Issued Unknown." and "Latest issue: Unknown" (W: `WeekEvidence.tsx:24,35`), which is accurate; Yogi is told that a lexical sort ranks `Unknown` above any ISO instant (Task 6).
- **E17, field values.** `unit`: `AQI` for Air, `UV index` for UV, `category` for Pollen and Outdoor mold (the fixture's convention, W: `week-evidence-preview.ts:36`). `basis`: `daily maximum` on every row, including null rows, where it names the series the date belongs to; nothing is pooled because a null value is never compatible (W: `week-evidence-preview.ts:43`). `source`, from a frozen table keyed by a stored code and de-duplicated by the screen into "Dataset" (W: `WeekEvidence.tsx:24`): `AirNow monitoring station, measured, preliminary`; `Open-Meteo with the CAMS air quality model, modeled` (DS-036's attribution, S:1078); `Open-Meteo forecast model, modeled`; and `Not recorded` for a row with no source. No upstream text (AirNow `SiteName`) is ever emitted (W: `docs/backend/checkpoint.md:330`). `context`: the context id string.
- **E18, `complete: true` means nothing was withheld.** The range is bounded (E15) and read whole, so the answer always holds every row there is. This is the reading the frontend's own fixtures use: `complete: true` with one row (W: `test/ui/production-review-refinements.spec.ts:37`) and with Air rows only (W: `test/ui/production-performance.spec.ts:24-25`). Reading it as "every date has a value" is rejected: the fixtures contradict it and nothing renders it (D: 7).
- **E19, availability and errors.** 401 without a session. 0025 missing (probe PGRST202, 42883, PGRST205 or 42P01) is a non-retryable 503 `feature_unavailable`. Any other database error is the house 500. No top-level `data` key (W: `runtime.ts:149-153`). No outbound network call from the read route.
- **E20, `GET /api/profile` emits `home_context`.** The runtime's `homeContextId` is `session.profile?.home_context?.id ?? session.profile?.profile?.home_context_id ?? null` (W: `ProductionApp.tsx:41`), and the profile it reads comes from `GET /api/profile` (W: `components/stage/StageSession.tsx:137,172`). That GET returns neither field (W: `app/api/profile/route.js:66-107`); only the PATCH adds `home_context` (W: `:230`). So today every production session has a null context and the validator would reject every real context id. The frontend's type declares `home_context?: {id, revision?}` (W: `lib/frontend/types.ts:20`) and its own production fixture serves both fields (W: `test/ui/production-fixtures.ts:9`). The GET adds `home_context: contextSummary(current)` (W: `lib/homeContext.js:104`), the PATCH's shape, or `null` when there is none or 0016 is missing. A failed context read omits the key and logs, as the household read does (W: `app/api/profile/route.js:63-80,114-123`); the profile answer never fails because of it.
- **E21, provider budget.** No B08 code calls Mapbox, Google Pollen, NWS or OpenUV. The recorder makes exactly one AirNow call per run and, per distinct stored point (3 decimals, as stored; no further rounding, per DS-034's "not arbitrary home rounding", S:1074), at most two Open-Meteo calls. A per-run point budget `DAILY_MAXIMA_MAX_POINTS` (default 400) and a 45-second deadline stop it early; untouched days stay `pending` or absent and the next run takes them, inside E4's window. Every provider request has the 20-second timeout of `lib/mapLayers.js:116`. The run's JSON reports counts only.
- **E22, recording is not behind a capability flag.** It collects the same class of data `daily_scores` already holds (dated environmental values at the home's point, W: `docs/backend/privacy-and-retention.md:16`), no free text, and a flag that defaults off would cost every day it stays off. The read route is not flagged either. Retention stays open and is tracked (Open question 1).
- **E23, the context link cascades.** `(profile_id, home_context_id)` references `home_contexts (profile_id, id)` **on delete cascade**, a deliberate difference from `daily_scores`' `no action` (W: `supabase/migrations/0016_home_contexts.sql:226-243`). B07's clear-all deletes `daily_scores` before `home_contexts` and names no other table (W: `docs/backend/plans/b07-privacy.md:84`); under `no action` it would raise 23503 once any maxima exist. Cascade lets it work without editing 0024. The 0016 concern, that a stray delete takes a stay's history, is answered by service-role-only access: nothing else deletes contexts.
- **E24, copy.** Every server-authored string (missing reasons, source labels, error envelopes) is in one frozen table with no U+2014 (AGENTS.md).
