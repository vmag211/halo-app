## What this package is, and what it deliberately leaves out

Four registry operations drive the Settings privacy panel, `ProductionPrivacy` (W: `components/production/ProductionPrivacy.tsx:14-27`), mounted by `SettingsPrivacy` (W: `components/expanded/SettingsPrivacy.tsx:21`). No route exists for any of them (no `app/api/privacy` directory). Today the panel reads "Privacy requests are unavailable." for every household, because `privacy.status` 404s and `verified` is false (W: `ProductionPrivacy.tsx:18,26`).

**In scope:**

- `privacy.status`, GET `/api/privacy/status` (W: `lib/frontend/production/runtime.ts:86`).
- `privacy.inspect`, POST `/api/privacy/export/inspect` (W: `runtime.ts:87`), minting a signed, stateless review token (P6).
- `privacy.export`, POST `/api/privacy/exports` (W: `runtime.ts:88`), a JSON receipt carrying `file:{name,mime,text}` (P8).
- `privacy.clear`, POST `/api/privacy/clear` (W: `runtime.ts:89`), scopes `journal` and `all`, both through one atomic database function (P3).
- Migration **0024**: functions and a trigger only, no table (P3, P4, P5, P7, P11).
- A `privacy` overlay in `GET /api/operations` that rebuilds an export file on reconcile inside a short window and never from storage (P9).
- A single per-table privacy inventory, `lib/privacyInventory.js`, and two structural tests that fail when a new owned table is not placed for both export and clear (P2, P12).
- A new server secret, `HALO_PRIVACY_REVIEW_KEY`, and its documentation (P6, Task 8).

**Dropped, with reasons:**

- **`forecast.read`.** Decision-blocked (D-F1 place handling, D-F2 AirNow and Pollen rights, D-F3 horizon semantics). *Unblocked by:* those three decisions.
- **CSV exports.** The client accepts `text/csv` (W: `ProductionPrivacy.tsx:23`), but nothing asks for it and a multi-table export has no honest single CSV shape. JSON only. *Unblocked by:* a product request naming the table it wants as CSV.
- **A stored export artifact or download link** (BE-226's "safe private download with expiry"). The contract delivers the file inline in the receipt (W: `docs/continuation/FRONTEND_INTEGRATION_READY.md:82`), so nothing is stored (P8, C12).
- **Clearing the frontend workspace collections on the server**, `weekJournal` included. They have no backend storage: `workspace.load` and `workspace.execute` (W: `runtime.ts:22-23`) have no route (`app/api/frontend` holds only `actions`). P13 rules what Clear Journal can honestly do today.

**Blocked, not planned:**

- **Account deletion through this panel.** "It is not account deletion." (W: `FRONTEND_INTEGRATION_READY.md:80`). `DELETE /api/account` stays the one identity-deletion path (W: `app/api/account/route.js:129-145`).
- **Export of `home_risks` fields.** The table predates the migrations and its deployed columns are unverified (W: `docs/backend/privacy-and-retention.md:17`; `supabase/baseline/reconstructed_baseline.sql:165-169`), so no allowlist can be written. It is counted and named in the manifest with a warning, and deleted by clear all (P2). *Unblocked by:* re-running `docs/backend/baseline-audit.sql` and adding its columns to the allowlist (Open question 6).

## Vibhav's decisions, restated (binding)

- **D-P1, clear all deletes everything but the login.** Every household-owned record, home, home history, household answers and settings included, so the person goes back through onboarding. The auth identity survives. This is not account deletion.
- **D-P2, export is everything the household owns,** through per-table column allowlists, never internal fields (tokens, hashes, ledger internals, recovery challenge material).
- **D-P4, Clear Journal clears both journals** (`symptom_logs` and the frontend week journal) and every season summary derived from them.
- **D-P5, the person's own export includes their email and the rounded home location.**
- **D-P3 is open**, and this plan rules it at the shortest the contract allows (P10), flagged as Open question 1.

- **P3, one atomic database function performs both clears and settles its own ledger row** (the B06 H8 pattern, W: `supabase/migrations/0023_household_actions.sql:39-66`; the B04 S15 pattern, W: `0021_settings_preferences_and_alerts.sql:558-576`). `public.clear_household_records(p_profile_id uuid, p_operation_id uuid, p_scope text, p_fingerprint text) returns jsonb`, migration 0024, one transaction, in this order:
  1. Lock the profile `for update` (so concurrent foreign-key inserts, which take `for key share` on it, wait for the clear), matching the lock order every writer already uses: profile, then the operation's own ledger row, then notification, band and preference rows (W: `0021_settings_preferences_and_alerts.sql:577-583`).
  2. Lock this operation's ledger row, which must be this household's, in domain `privacy`, kind `privacy.clear.<scope>`, still `pending`; otherwise `HALO_OPERATION_NOT_PENDING`, nothing written.
  3. Recompute the review fingerprint (P6) and compare it with `p_fingerprint`; a difference raises `HALO_REVIEW_CHANGED`.
  4. For `all` only: refuse with `HALO_BUSY` while any other `operations` row of this household is `pending`, or any `luna_runs` row is `queued` or `generating` with `updated_at` inside the 120 s window (BE-263's "first blocks new private writes", S:772; W: `lib/operations.js:64`). For `journal`: refuse only on another pending `privacy` row.
  5. Delete per P2, every statement `where <owner> = p_profile_id`. For `all`, in foreign-key-safe order: `luna_conversations` (cascading turns and runs, W: `0020_luna_conversations.sql:117,126,138`), `daily_scores` before `home_contexts` (the composite key is `on delete no action`, W: `0016_home_contexts.sql:236-243`), then `home_risks`, `symptom_logs`, `alerts`, `notification_prefs`, `household_bands`, `push_subscriptions`, `profile_preferences`, `explore_areas`, `household_actions`, `household_action_preferences`, `household_action_state`, and `operations` where `operation_id <> p_operation_id`. For `journal`: `symptom_logs`, and `alerts` where `type = 'season_summary'`.
  6. For `all`: reset the profile (P4).
  7. Settle the own ledger row `succeeded` with the minimal receipt `{operationId, status: 'succeeded', scope}` (P10).
  8. Return `{receipt, removed}`, where `removed` is the total row count, for tests and logs only, never emitted.

  So a deletion exists if and only if its operation is `succeeded`, which makes the client's "The request was not applied. Your data is unchanged." (W: `ProductionPrivacy.tsx:23`) true for every `failed` this package can produce: a refusal, an in-process throw (W: `lib/operations.js:171`) and a reap (W: `lib/operations.js:284`) all leave nothing deleted. It is race-safe against the reaper for the reason B06 H8 gives: both are conditional on `status = 'pending'`. This closes traps P-6, P-10 and P-13.

- **P4, the clear's own receipt and the profile survive; the profile is reset, not deleted.** Deleting the profile would delete the receipt: `operations.profile_id` cascades from it (W: `0017_operations_ledger.sql:46`), and reconcile would then 404 (trap P-8's sibling, digest section 6). Deleting the profile is also unsafe on its own terms: `handle_new_user` makes the row only on an auth insert (W: `0001_anon_auth.sql:17-41`), so a surviving login with no profile would be a state no route expects, and every owned table's foreign key points at it. So the profile row keeps `id` and `created_at` (which mirrors the sign-up time) and every other column returns to its default: `address`, `lat`, `lng`, `zip`, `county`, `pwsid`, `build_year`, `water_source`, `home_year` (baseline, W: `supabase/baseline/reconstructed_baseline.sql:128-142`), `state` (0009), `onboard_request_id` (0014), `tenure` (0021) to null; `renter_mode` to `false` and `locale` to `'en'` (0002). With `lat` and `lng` null, `GET /api/profile` answers `onboarded: false` (W: `app/api/profile/route.js:82`), which is what sends the person back through onboarding (W: `app/OnboardingScreen.tsx:97`). The 0021 triggers run as for any profile write: `reconcile_profile_tenure` leaves a null tenure with `renter_mode` false alone, and `profiles_settings_revision` touches a preferences row the function has already deleted (W: `0021_settings_preferences_and_alerts.sql:384-425,487-520`). `recovery_challenges` are kept: they are proof material about the login, which D-P1 keeps, and deleting a pending `link` row while the provider still holds the address change would leave `account.read` and the provider disagreeing (Open question 2). Every other ledger row of the household is deleted once settled; a pending one refuses the clear (P3 step 4), so no in-flight surface loses its claim.

- **P5, export allowlists, two tiers, never the client's regex.** Columns are named per table (P2); a column not named is not read (`select` lists columns explicitly, never `*`). `privateText: false` exports the `base` tier only; `true` adds `private`. The tier assignment follows what the client treats as private (W: `settings-preview.ts:38`: notes, symptoms, severity, illness, bands, messages, body) translated to real column names, which is the point of trap P-12: `possibly_illness`, `zip`, `endpoint`, `p256dh` and `auth` are each placed by name, not by a pattern. D-P5 supersedes the client's rules for exactly two fields: `email` and the rounded home coordinates are `base`. Coordinates are rounded again to 3 decimals at export (`Math.round(x * 1000) / 1000`), because legacy rows predate the rounding (W: `0009_daily_details_and_state.sql:27-30`); legacy `address` and `zip` are never exported, so `exactLocation: 'excluded'` in the file header is true. The conversation group without private text is `{excluded: 'Private text was not selected.'}`, as the client does (W: `settings-preview.ts:57`). Stored content is exported verbatim (BE-053, S:434; C8).

- **P6, the review token is stateless, signed with its own key, and binds owner, selection and records.** Token = `base64url(payload) + '.' + base64url(mac)`. `payload` = `{v: 1, s: scope, g: groups sorted, p: privateText, e: expiry in epoch seconds, n: 16 random bytes}`; nothing about the household is in it. `mac` = HMAC-SHA256 under `HALO_PRIVACY_REVIEW_KEY` over `'halo:privacy-review:v1'`, the verified `profile_id`, the payload and the fingerprint. So the owner and the fingerprint are bound without being disclosed, and a token minted for one household fails for another (HO-066). The key is **not** `HALO_RECOVERY_TOKEN_KEY` (W: `lib/recovery.js:195`; digest 8.3): a separate variable keeps rotation of one from invalidating the other. It has the same 32-character floor and the same refusal to fall back to a default (W: `lib/recovery.js:176-199`); with no usable key, privacy is unavailable from `privacy.status` (P11). The fingerprint is `public.privacy_fingerprint(p_profile_id uuid, p_tables text[]) returns text` (0024): the SHA-256 (core `sha256(bytea)`) of, per listed table in a fixed order, the sorted `md5(row_to_json(...)::text)` of the household's rows. It covers only tables a person's own actions write: `profiles` (the reset columns only), `home_contexts`, `household_bands`, `symptom_logs`, `notification_prefs`, `push_subscriptions`, `profile_preferences`, `explore_areas`, `household_actions`, `household_action_preferences`, `luna_conversations`, `luna_turns`. Server-written rows (`daily_scores`, written on every cache-missing app open; `alerts`; `home_risks`; `luna_runs`; `household_action_state`; `operations`) are counted and removed but not bound, so a background refresh between review and confirm does not refuse a clear the person asked for. The function refuses any table name outside that list (`HALO_INVALID_INPUT`), and Task 4 pins the list against `lib/privacyInventory.js`. For `journal` the fingerprinted table is `symptom_logs`; for `all`, every listed table; for `export`, the listed tables of the selected groups. The fingerprint never leaves the server.

- **P7, the typed `DELETE` is the client's; the token is the server's proof.** There is no confirmation word on the wire (trap P-5; W: `ProductionPrivacy.tsx:24`), so `app/api/account/route.js:138` is not reused. Export and clear bodies are exactly `{reviewToken, scope, operationId}`; any other key is a 400. Clear scopes accept `groups: []` at inspect (trap P-3).

- **P8, the export file travels inline and is never stored.** Success is `{operationId, status: 'succeeded', file: {name, mime, text}}` (W: `FRONTEND_INTEGRATION_READY.md:82`). `name` is `halo-export-YYYY-MM-DD.json` (the household's local date), which passes `/^halo[-\w]*\.(json|csv)$/` and names no household (UI-146); `mime` is exactly `application/json` (no charset suffix, W: `ProductionPrivacy.tsx:23`); `text` is the export document as JSON, two-space indented. `runOperation`'s `execute` returns only the minimal receipt and keeps the file in a closure (the B06 H8 closure pattern), so `operations.result` never holds record content (trap P-8; W: `0017_operations_ledger.sql:41-42`; W: `lib/operations.js:174`). The document: `{format: 'halo-export-v1', generatedAt, scope: 'export', groups, privateText, exactLocation: 'excluded', manifest: {schemaVersion: 1, counts: {<group>: {<table>: n}}, omitted: [{table, reason}], warnings: [...]}, <group>: {...}}` (BE-331). It never carries the wireframe's `origin: 'isolated-wireframe'` or `authoritative: false` (W: `settings-preview.ts:46`). **Size:** the whole serialized response must be at most 4,000,000 bytes, under the 4.5 MB platform body limit (digest trap P-7, unverified against the plan) and far under the client's 10,485,760 UTF-16 units. Inspect builds the document to count it, so it refuses an oversize selection first with a **422** `export_too_large` (the client's `validation`, no lock, the review not opened); an export that grew past the cap after inspect answers 200 `{operationId, status: 'failed', reason: 'too_large'}`, which is true (exports change nothing). Reads page through `range()` at 1,000 rows ordered by primary key until a short page, so PostgREST's `max_rows` never truncates silently (B06 F1).

- **P9, reconcile rebuilds an export inside a short window, from a selection, never from storage.** The stored export receipt is `{operationId, status, scope: 'export', selection: {groups, privateText}}`: two group names and a boolean, not content. In `GET /api/operations`, a succeeded `privacy` row of kind `privacy.export` created within the last **10 minutes** (the token's lifetime, P10) is answered with `file` rebuilt from the current rows with the stored selection, under the same size cap; after the window it is answered as stored, without `file`. The client then keeps its lock with "The export is not ready to download. Check its status." until a reload, after which `privacy.status` no longer lists the settled row and the panel unlocks (digest 5, reading (a)). That is honest and private: no artifact exists to leak, and a person who reconciles within minutes still gets the download. A replayed `POST /api/privacy/exports` with the same id follows the same rule. The rebuilt file reflects the rows at rebuild time and says so (`generatedAt`). This is the S14/S16 overlay idea (W: `app/api/operations/route.js:16-48,127-152`) applied to a file: the stored receipt is history, the live answer is computed. `privacy` is not added to `LIVE_LIST_PATHS`: no privacy receipt carries an `unresolvedOperations` list.

- **P10, D-P3 retention, at the shortest the contract allows** (Open question 1):
  - **Review token:** stored nowhere. `expiresAt` = mint time plus **10 minutes**: long enough to read the preview and type `DELETE`, with margin for a device clock a few minutes fast (the client rejects a past `expiresAt` by its own clock, W: `ProductionPrivacy.tsx:22`).
  - **Export file:** stored nowhere, at any point (P8); rebuilt on reconcile only within those 10 minutes (P9).
  - **Export and clear receipts:** ordinary ledger rows in domain `privacy`, holding only `{operationId, status, scope}` (and the export's selection), purged **24 hours** after they settle. A settled receipt is needed only by an open page that lost its answer and presses "Check request status"; after a reload nothing holds the id (the client's `unknown` is in-memory state, W: `ProductionPrivacy.tsx:16,19`). The purge is `public.purge_privacy_receipts(p_profile_id uuid default null) returns int` (0024): owner-scoped and lazy on every `privacy.status` read (the reaper's "settle where the inventory is read" pattern, W: `lib/operations.js:258-290`), and global once a day from the existing cron. Pending rows are never purged; the reaper owns them. After a clear all, its own receipt is the only household row left besides the reset profile and recovery material, and it is gone a day later (BE-332's "minimum non-content receipt").
  - Logs carry operation ids, scopes, counts and error codes only; never a token, a fingerprint or a row (`loggableError`, W: `app/api/operations/route.js:175-177`).

- **P11, availability is reported by `privacy.status`, never first discovered by a mutation** (trap P-11). Status answers a non-retryable 503 `feature_unavailable` when the review key is missing or short, when 0017 is missing, or when 0024 is missing (probed through `public.privacy_schema_version()`, a trivial function in 0024, PGRST202 or 42883). The client shows its own "Privacy requests are unavailable." with Try again (W: `ProductionPrivacy.tsx:26`). Inspect, export and clear check the same things again before any ledger claim and answer the same 503, which the client reads as `unknown_outcome` only on export and clear; status has already reported it, so a person cannot reach them in that state through the panel. **Missing tables in a lagging environment:** 0024 asserts at apply time that the 0016, 0017, 0020, 0021, 0022 and 0023 objects exist and refuses to apply otherwise, so wherever the clear function exists every table it deletes from exists. The export builder still degrades table by table: a missing table (PGRST205 or 42P01) is zero rows plus a manifest warning naming it as not stored on this deployment; a missing optional column (42703 or PGRST204) drops that column with a warning, the daily-score precedent (W: `app/api/daily-score/route.js:245-279`). A failed read of a table that exists fails the inspect or export with a 500, because `count` has no "unknown" value. On inspect that costs nothing: nothing was claimed or minted, and the client's inspect only sets a message and takes no lock (W: `ProductionPrivacy.tsx:22`).
