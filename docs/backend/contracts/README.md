# HALO executable API contracts

One document per build package, each covering only the operations that package changed. `b01.openapi.json` is version `b01-1` (six B01 operations), `b03.openapi.json` is version `b03-1` (the six Luna operations B03 built), `b04.openapi.json` is version `b04-1` (the four settings and alerts operations B04 built, plus the reconcile both clients use), `b05.openapi.json` is version `b05-2` (the six discovery operations B05 built or fixed, with the public map reads of Task 6 and the city and ZIP places of Task 8) and `b06.openapi.json` is version `b06-1` (the four My Week operations B06 built, plus the `actions` and `week-updates` half of the reconcile). All are OpenAPI 3.1 with the same shape: a `paths` map whose statuses are the ones the handlers can actually produce, synthetic `{ operationId, status, body }` fixtures under `fixtures/<package>/`, and an Ajv 2020 conformance suite that runs the real handlers through the isolated route harness. None certifies a deployment, a provider right or a source's meaning.

## B11 Homeguard workspace contract

`b11.openapi.json`, version `b11-2` (2026-10-25: `weekJournal` stored through migration 0034 while `HALO_FEATURE_JOURNAL` is on, and the `journal_day_taken` refusal), has the same shape as the documents above. It documents `workspaceLoad` (`GET /api/frontend/workspace`, registry `workspace.load`), `workspaceExecute` (`POST /api/frontend/workspace/commands`, `workspace.execute`) and `operationsRead`, which here covers only the `workspace` domain of `GET /api/operations`. `test/contractsB11.test.mjs` is its conformance suite. It works like the B06 one, and adds three things.

- **The client's own modules judge every answer.** `createProductionRuntime` (its status mapping, headers and unwrap), `createHomeAdapter`, `validHomeRecords`, `validHomeChanges`, `homeReceiptCoversCommand`, `validProductionCollection` and `recordFingerprint` are the frontend's compiled files, not transcriptions. What the screen does with an answer is the provider's decisions, transcribed once in `test/helpers/frontendB11.mjs` from `HomeWorkspaceState.tsx` (a drift test pins its sentences to the component). The suite asserts what Homeguard then holds: the rows, the sentence shown, and whether it is locked on an operation. A 5xx on a save locks it, a refusal never does.
- **Below the routes everything is real.** The world is two households on PGlite with migration 0026's `read_household_workspace` and `commit_household_workspace` and the 0017 ledger (`test/helpers/workspaceWorld.mjs`). The scenarios: a new household loads fourteen ready collections and two unavailable ones (`weekJournal`, `homeTransitions`); a save, an update and a delete are confirmed by the canonical rows and kept after a reload; the receipt, the next load and the reconcile are the same rows; a second tab's stale save is refused with no lock; a lost answer locks and reconciles to "Saved."; a save pending on another device locks the load and its status check reports pending, failed or succeeded; a test, observation or note with a private file is refused and nothing is stored; `clear-private` is refused and every record stays held and stored; removing notes takes their cases with them; the capability off and migration 0026 missing.
- **Each fixture carries its `request`.** A fixture under `fixtures/b11/` is `{ operationId, status, request, body }`: the normalised answer a real handler gave in the suite, with the load's collection or the command that led to it. The suite replays each one through the client with the operation id swapped for the id the client generated, so a fixture that the client would misread fails. Fixtures without a `request` (an unparseable or oversized body) are replayed with a plain test write.

The 200 refusals are the document's central point. A refused save is `{ operationId, status: 'failed', changes: {}, code, reason, message }`, 200, so the client keeps its draft and does not lock; `changes` is required for every status because the adapter throws without it. The ten reasons (`stale_revision`, `notes_changed`, `invalid_reference`, `limit`, `project_guide_locked`, `invalid_record`, `attachments_unavailable`, `clear_unsupported`, `week_journal_unavailable`, `home_transitions_unavailable`) each have a fixed code and sentence that the suite pins to `lib/workspaceStore.js`; the first five are recorded on the ledger and replay the same body, the rest are decided before any claim and record nothing. Each `Record_<collection>` schema is held against the client's own row check on a corpus of valid and broken rows, so a row the document admits is a row the client keeps.

Several constraints describe this release, not the operations for ever: `Record_tests.attachments` has `maxItems: 0` and `Record_exploreNotes.photoAttachment` is forbidden (Ruling W4), `WorkspaceSnapshot` has no `revision` or `nextCursor` (Ruling W6), `weekJournal` and `homeTransitions` can only be answered unavailable (Rulings W2, W3), and `WorkspaceClearPrivate` can only be refused (Ruling W9). The status `unknown` is documented for a reconcile whose reap failed; a real stale pending row is reaped by its own read and answered as `failed` (fixture `operationsRead-workspace-reaped`).

Run `node --test test/contractsB11.test.mjs`, and `node test/contractsB11.test.mjs --write-b11-fixtures` to rewrite the fixtures after a deliberate contract change. Migration 0026 is applied nowhere and `HALO_FEATURE_WORKSPACE` is set in no environment, so nothing here has run against a real Supabase project.

## B07 privacy contract

`b07.openapi.json`, version `b07-1`, has the same shape as the documents above. It documents the four operations the Settings privacy panel (`components/production/ProductionPrivacy.tsx`) calls: `privacyStatus` (`GET /api/privacy/status`), `privacyInspect` (`POST /api/privacy/export/inspect`), `privacyExport` (`POST /api/privacy/exports`) and `privacyClear` (`POST /api/privacy/clear`), plus `operationsRead` for the `privacy` domain of `GET /api/operations` only. Each names its registry entry in `x-halo-operation`. There are 56 fixtures under `fixtures/b07/`, every one the normalised answer of a real handler, and a test fails if one drifts. `test/contractsB07.test.mjs` is the conformance suite. It goes further than B06's in three ways.

- **The database under it is real.** Every world is two households on PGlite with every migration applied: the 0017 ledger with 0024's settled-privacy guard, 0024's five functions called by argument name, and, for the privacy routes and the reconcile, the household tables read straight from PGlite (`test/db/pgliteSelect.mjs`). So the inspect-to-export run builds its file from the rows the real fingerprint was computed over, and a clear is proved by the rows it left.
- **The panel's whole consumption logic judges every answer.** `test/helpers/frontendB07.mjs` holds `ProductionPrivacy.tsx:18-25` (`verified`, the first-entry lock, `selected`, `inspect` with its guards and validator, `accept`, `confirm` with its guards, `reconcile`) and the settings gate (`SettingsWorkspace.tsx:52`) as the component's own lines, which a drift test requires the component to contain, with their TypeScript annotations removed and nothing else changed. Each scenario ends in what the panel shows: verified or not, the lock and its scope, the open review, the sentence, the file it downloaded. A negative control per transcribed function compiles a deliberately altered copy and shows a scenario failing on it.
- **Every real answer is checked as it happens.** Each call to a documented route is checked against the document (status, body schema, an export file's `PrivacyExportDocument`), for the `X-Request-Id` echo, the bare body, U+2014 and anything proof-bearing in an error envelope, including calls the client runtime makes (a failure there is reported, not mistaken for a network error).

The scenarios: a new household loads verified with no lock and a review opens with the server's count; an export downloads and unlocks; a lost export reconciles to the download inside ten minutes and to the kept lock "The export is not ready to download. Check its status." after, and a reload unlocks; a real pending export and a real pending clear are each listed by `privacy.status` with their scope and lock a new page until reconciled; Clear Journal ends in "Journal cleared." with the database proving AC-282; clear all ends in "Your records were cleared." with the settings gate still passing and the household not onboarded; a lost clear reconciles to its outcome and a reaped one to "The request was not applied. Your data is unchanged." with nothing changed; a stale review is the 409 with the review left open.

Both export success shapes are documented and fixtured: `{operationId, status: 'succeeded', file}` from the route and from a reconcile inside the window, and `succeeded` without `file` from a reconcile after it. A clear's success carries its `scope`. Every 200 `failed` reason (`too_large`, `abandoned` for export; `review_changed`, `busy`, `abandoned` for clear), both 409 reasons (`review_changed`, `operation_mismatch`) and the in-flight 503 have a fixture. The review token in a fixture is the placeholder `review-token` (a real one is a capability), and `expiresAt` is fixed in the future so the client's own check accepts it. No B07 body has a top-level `data` key or a U+2014.

The registry entries and the route files agree: every registry path (`runtime.ts:86-89`) resolves to a route file with the declared method and `maxDuration = 60`. The ledger kinds are one table, `PRIVACY_KINDS` in `lib/privacyStore.js`, which the export and clear routes write and `privacy.status` maps back to a scope.

Run `node --test test/contractsB07.test.mjs`, and `node test/contractsB07.test.mjs --write-b07-fixtures` to rewrite the fixtures after a deliberate contract change. Migration 0024 is applied nowhere and `HALO_PRIVACY_REVIEW_KEY` is set in no environment, so nothing here has run against a real Supabase project.

## B06 My Week contract

`b06.openapi.json`, version `b06-1`, has the same shape as the documents listed above. It documents `actionsLoad` (`GET /api/frontend/actions`), `actionsCommit` (`POST /api/frontend/actions/commands`), `weekChanges` (`GET /api/week/changes`), `weekAcknowledge` (`POST /api/week/changes/acknowledge`) and `operationsRead`, which here covers only the `actions` and `week-updates` domains of `GET /api/operations`. Each operation names its registry entry in `x-halo-operation`. There are 60 fixtures under `fixtures/b06/`. `test/contractsB06.test.mjs` is the conformance suite. It goes further than B05's in three ways.

- **It judges answers by what the client does with them, not only by their shape.** Every real handler answer and every fixture is run through the client's own code, transcribed once in `test/helpers/frontendB06.mjs`: the runtime's status mapping and unwrap, the action adapter, My Week's load, save and reconcile decisions, and the week strip. The suite then asserts the client's state: whether My Week is ready, whether it is locked and on which operation, and which sentence it shows. For example, a 409 must clear without a lock, a 5xx on a save must lock and reconcile, and a reconciled `failed` must say "No save was applied" and reload.
- **Every fixture is a real handler's answer.** Each fixture is the normalised body a handler produced in that file, with ids renumbered and timestamps fixed. A test fails if any fixture drifts from today's handler. After a deliberate contract change, regenerate them with `node test/contractsB06.test.mjs --write-b06-fixtures`.
- **The routes agree with each other.** A save's receipt snapshot is the next load. A reconcile is the current snapshot plus the live unresolved list, the same list at the top level and at `snapshot` (Ruling S16). The empty household is the same bytes, `{"actions":[],"metas":{},"preferences":{},"unresolvedOperations":[]}`, on the load, a receipt and its reconcile. A drift test also holds `lib/actionRules.js` (the server's copy of the client's rules, Ruling H15) to the independent transcription on a shared corpus.

Several schema constraints describe this release, not the operations for all time:

- `WeekChanges.changes` has `maxItems: 0`, because no change source exists (Ruling H4).
- `WeekAcknowledgeRefused` can only be `failed` (Ruling H19).
- `ActionSnapshot` forbids `reminderStates`, because there is no scheduler.
- `ActionsCommand` has no `clear` kind (Ruling H14).

A 200 refusal's `message` is fixed per reason, and an `invalid_result` refusal carries the client's own sentence. The ledger stores a code (`check`, Ruling H33), which `operations.read` replays. The tasks capability is off by default, so `actions.load` and a succeeded `actions` reconcile answer the non-retryable 503 while it is off, and a save answers a 200 `failed` receipt with the disabled reason and no ledger row (Ruling H17).

Run `node --test test/contractsB06.test.mjs`. Migration 0023 was applied to production on 2026-10-19, and the flag is on in no environment. Nothing here has run against a real Supabase project.

## B10 forecast contract

`b10.openapi.json`, version `b10-1`, documents one operation, `forecastRead` (`GET /api/forecast`, registry operation `forecast.read`), the outdoor planner's forecast snapshot for one date at the saved home or a typed North Carolina place. `info.x-halo-rulings` carries F12 (date-only, inclusive, zone-local horizon), F17 (the two meanings of `issuedAt`), F18 and F18-S (expiry and stale serving), F19 (content versions) and F21 (statuses). The 503's log-only reason tokens, `open_meteo_incomplete` among them, are listed in its description and never sent.

- **It runs the client's whole path.** `test/contractsB10.test.mjs` uses the real `createProductionRuntime` (loaded as the frontend tests load it), whose fetcher is the real route handler, so query building, status mapping and the envelope are the client's own code. The hook's handling, the validator and the outdoor planner's decisions and text are transcribed in `test/helpers/frontendB10.mjs`, with a drift test against the working tree. Each scenario asserts what the screen shows, including the save that becomes a B06 task.
- **Every fixture is a real handler's answer**, captured with a fixed clock and the request id `b10-contract-0001`. Regenerate after a deliberate contract change with `node test/contractsB10.test.mjs --write-b10-fixtures` and review the diff.
- **The schema is stricter than the validator in one place on purpose.** The client checks only that `coverage` exists; a non-string value would pass it and break the render, so `Coverage` requires four strings, each beginning with the place.

Several schema constraints describe this release: `air` and `pollen` are always `null` (AirNow is daily, C1; no free pollen source), and `changedMessage` is forbidden (no change service). AirNow (Task 5) is not connected, so production answers say air was not checked; the suite stands an adapter in through `lib/forecast/airNowSlot.js` and also runs with the slot empty. Weather data is by Open-Meteo.com under CC BY 4.0, credited in Weather coverage. Run `node --test test/contractsB10.test.mjs`. Nothing here has run against a real provider, Upstash or Supabase project.

## B04 settings and alerts contract

`b04.openapi.json`, version `b04-1`, documents `settingsRead` and `settingsSave` (`GET` and `PATCH /api/settings`), `alertsRead` (`GET /api/alerts`, the legacy read with the contract inbox added) and `alertsUpdate` (`POST /api/alerts/state`), plus `operationsRead` (`GET /api/operations`) for the settings and alerts domains only, because that is how both clients clear a parked operation. Each names its frontend registry entry in `x-halo-operation`. `capabilities.read` and `evidence.read` were dropped before execution and are not documented. `test/contractsB04.test.mjs` is the conformance suite, and it follows the B05 one:

- **The frontend's own code judges every answer.** `validSettingsSnapshot`, `validAlertSnapshot` and `alertReceiptCovers`, and the two client hooks (`ProductionPreferences` with the workspace's save body, and `useProductionAlerts`), are transcribed once, in `test/helpers/frontendB04.mjs`, and shared with `test/routesSettings.test.mjs` and `test/routesAlertsState.test.mjs`. One test shows the validators refusing what the client refuses. Every success fixture and every real handler answer must be one the client handles, and no error fixture may. The one deliberate exception is the alerts read before 0021, which is served (Ruling S10) and which the client refuses as unverified.
- **The routes agree with each other.** A settings read's revision is accepted by a save, and each receipt's revision is the next `If-Match`. The one before it is a `stale_revision` naming the current one. A save and an alerts change answer with the live unresolved list minus themselves, the ledger keeps `[]` (Ruling S14), and a reconcile through `GET /api/operations` carries the live list minus itself (Ruling S16): at `snapshot.unresolvedOperations` for settings, and at the top level for alerts. The clients' own hooks clear a parked operation in one check.
- **Headers are checked both ways.** Response headers (`X-Request-Id`, and `Retry-After` on the auth outage only) and request headers (`Idempotency-Key`, `If-Match`, and the ignored `X-Halo-Home-Context`) are checked in both directions.

Each mutation's `409` lists every reason its handler emits. For settings, these are `stale_revision` (with the current revision), `home_changed`, `operation_mismatch`, and, on a replay, `operation_failed` and `operation_abandoned`. For alerts, they are `stale_selection`, `operation_mismatch`, `operation_failed`, `operation_abandoned` and `operation_cancelled`. A settings save whose ledger row the reaper settled before `save_settings` ran answers the first call with `200 {operationId, status:'failed'}`, so the client says "The save was not applied. Your draft is still here." and keeps the draft. Only a replay of that id is the `409`. `unresolvedOperations` is a lock, not a log (Ruling S1). Before 0021, settings and `alerts.update` answer a non-retryable `503`, while `alerts.read` keeps its legacy keys and never answers `503` (Ruling S10).

Run `node --test test/contractsB04.test.mjs`. Migration 0021 was applied to production on 2026-10-19, but nothing here has run against a real Supabase project. Fixtures were captured from the real handlers on the isolated harness, with synthetic ids and the request id `b04-contract-0001`.

## B05 discovery contract

`b05.openapi.json`, version `b05-2`, documents `mapLayer` (`GET /api/map`), `mapDistrict` (`GET /api/district`), `locationsSearch`, `exploreAreaRead` and `exploreAreaSave` (`GET` and `PATCH /api/explore/area`) and `mapComparison` (`GET /api/map/comparison`). Each operation names its frontend registry entry in `x-halo-operation`. `community.read` and `map.brief` were dropped and `organizations.search` and the summaries trio are blocked, so none of them is documented. `test/contractsB05.test.mjs` is the conformance suite, and it follows the B03 one:

- **The frontend's own code judges every answer.** `validPlaces`, `validDiscoveryArea`, `parseMapLayer`, `parseMapDistrict`, `parseMapComparisons` and `compareEvidence` are transcribed once, in `test/helpers/frontendB05.mjs`, and shared with the per-route suites. One test shows each of them refusing what the client refuses. Every success fixture and every real handler answer must pass them, and no error fixture may.
- **The routes agree with each other.** A `locations.search` candidate saved through `PATCH` and read back through `GET` is the same object on all three surfaces, and each returned revision is accepted as the next `If-Match`. Every id `map.layer` gives the client finds its record in `map.comparison`.
- **Headers are checked both ways.** Response headers (`X-Request-Id`, and `Retry-After` on the auth outage only) and request headers (`Idempotency-Key`, `If-Match`, and the ignored `X-Halo-Home-Context`) are checked in both directions. A header that is sent must be documented, and a documented header must be sent by some exercised call.

Some schema constraints are statements about this release, not about the operations for ever. `DiscoveryPlace` admits only North Carolina counties, Census places and ZCTAs (Ruling D4, widened by Task 8 after open question 2 was answered on 2026-10-19). `DiscoveryArea` forbids `pendingOperation` (D7). `ComparisonRecord` fixes `method` and `sourceVersion` to null, every `qualifier` to `unknown` and `coverage` to `partial`, and sends no `sourceName` (D3). So every comparison pair reads "Not comparable". The only way to change that is data acquisition (tracker HO-074), and it needs a new contract version. `MapDistrict` forbids the server-side `county_rankings`. The `PATCH` 409 lists every reason: `stale_revision` and `revision_exhausted` (both with the current revision), `operation_mismatch`, and, on a replay of an attempt that is over without a receipt, `abandoned` and `attempt_failed`. No B05 body has a top-level `data` key (D10).

Two operational notes. While the stored air layer is stale, `/api/map` can answer a live air build while the comparison answers 503, and the client then shows its blocked copy. And 2,000 comparison ids pass the server cap but exceed common URL limits (finding F4).

Version `b05-2` covers two changes, made together because neither had shipped as `b05-1` and nothing had consumed `b05-2`: Task 6's public map reads, below, and Task 8's widening of `DiscoveryPlace` from counties to North Carolina's Census places and ZCTAs, so its `id` now also admits `us-place:<GEOID>` and `us-zcta:<ZCTA5>`. A strict consumer of `b05-1` must accept both. Version `b05-2` (B05 Task 6, approved 2026-10-19) makes the three map operations public, and their `security` is `[{}, {"bearerAuth": []}]`: no credential is needed, and a bearer is still checked. A request with no Authorization header is an anonymous, cache-only read: answered only from what is stored, never built, stored or fetched, and a 503 when nothing is stored. The anonymous district answer is `MapDistrictPublic`, which forbids `household_county`. Each map operation documents the visitor limiter's 429 (60 a minute, `Retry-After: 60`) and `Cache-Control` and `Vary` on every status: `public, max-age=0, s-maxage=600` on a successful anonymous answer and `private, no-store` on everything else. Any Authorization header is checked as before, so the 401 now means a header that is not a valid session. A successful anonymous answer carries an `X-Request-Id` the server chose, never the caller's, because a shared cache serves it to every visitor; a cached copy carries the id of the request that filled the cache. Every private answer, anonymous refusals included, still echoes a well-formed client id.

Run `node --test test/contractsB05.test.mjs`. Migration 0022 was applied to production on 2026-10-19, but this suite runs only on the isolated harness, and the CDN's handling of the cache headers is a staging check for a person (`YOUR_TODO.md` 1.4), so nothing here has run against a real Supabase project or CDN.

## B03 Luna contract

`b03.openapi.json`, version `b03-1`, documents `lunaCapabilities`, `lunaConversation`, `lunaClear`, `lunaMessage`, `lunaRunStatus` and `lunaRunCancel`. `test/contractsB03.test.mjs` is its conformance suite, and it does three things B01's does not.

**It transcribes the frontend's own validators and runs them on every response.** The client validates each Luna payload with `validLunaRun`, `validLunaConversation` or `validLunaCapabilities` from `lib/frontend/production/luna-service.ts` on `origin/codex/october15-review-refinement` (not checked out here; read it with `git show`), and **discards the whole payload** when one returns false, so a single wrong field loses the answer and the person's own question with it. The transcriptions are boolean predicates, and one test proves they reject what the client rejects, in both directions for the rule that is easiest to get backwards: a `completed` run must carry its conversation, and a `queued` one need not but may.

**It checks that the routes agree with each other.** One client function validates the conversation returned by `messages`, `runs/status`, `runs/cancel`, `conversations` and `clear`, and the component holds a single conversation pointer, so a divergence between any two of the five is a defect even with every route's own suite green. The suite asserts the five are byte-identical for the same state and carry the same five members, and that the two run routes answer the same run identically once it is settled. The `runs/status` and `runs/cancel` handlers deliberately still duplicate the five-line shape that decides this; the agreement is pinned here rather than by sharing that code.

**Two schema constraints are statements about this release, not about Luna for ever.** `LunaMessage` forbids `proposal`, `links` and `choices`, which the frontend's own type permits, and `LunaCapabilities` requires `tools` to be empty whenever `available` is true. Both encode the scope decision that Luna answers and cites and does not act: the four tool operations (`luna.proposal.edit`, `luna.proposal.cancel`, `luna.confirm`, `luna.operation`) are not built and are deliberately absent from this document. Building the tool half means a new contract version, and the suite will say so. **B20 (2026-10-25, `vmag211/luna-actions`) built the tool half behind `HALO_FEATURE_LUNA_ACTIONS`.** With that flag off, `b03-1` still describes every answer exactly. With it on, an answer may carry `proposal` or `choices` and `tools` is non-empty, which `b03-1` does not describe; no B20 contract document is written yet, and `test/routesLunaActions.test.mjs` checks those answers with the frontend's own validators instead.

Rules the frontend enforces that JSON Schema cannot express are listed in the schema descriptions and enforced by the transcribed validators instead: message ids unique within a conversation, a source url that parses as https with no embedded credentials, and evidence text that is non-blank after trimming. `LunaConversationData` requires all five members, which is stricter than the frontend, because `pendingRequest` and `unresolvedOperations` are what a reload recovers a parked attempt and parked operations from. `unresolvedOperations` is always empty in this release. The absent-conversation answer, `{ "data": null }`, is deliberately **not** a valid `LunaConversationData`: there is no valid empty conversation. It is an envelope on purpose, because the client runtime unwraps an own `data` key, so the component receives `null`, keeps the composer enabled, and sends `conversationId: null` to mean "start one". Any other empty object reaches the component as present but invalid and disables the composer.

Fixtures use reserved `example.test` hosts and obviously synthetic ids, and a test scans every one of them for secrets, tokens, bearer headers, provider names, street addresses and em dashes. No fixture is evidence about a real source.

Run `node --test test/contractsB03.test.mjs`. The capability flag is off in every environment (migration 0020 was applied to production on 2026-10-19), so nothing in this contract has run against a real model or a real Supabase project.

## B01 executable API contract

`b01.openapi.json` is OpenAPI 3.1, contract version `b01-1`. It documents six operations changed by B01, not the whole HALO API. Existing approved frontend types remain handwritten and unchanged; `test/contractsB01.test.mjs` checks actual handler responses against the executable schemas with Ajv 2020 and format validation. Types have not been generated or proven exhaustive against this document.

`fixtures/b01/` contains synthetic wrappers `{ operationId, status, body }`. Only `body` is the wire response. Error request IDs are synthetic. A fixture represents shape and semantics, not an exact wording guarantee. Headers are documented in OpenAPI and are not in the JSON fixture body. The route conformance test checks exactly two: `X-Request-Id` (echoed from the caller) and `Retry-After`, which is sent only with the retryable auth outage (503, `auth_unavailable`, 2 seconds). It checks both directions, but only for the operation and status pairs the test exercises: a documented header that no exercised response sent fails, and a sent header that the contract does not document fails. A rate-limit 429 does not send `Retry-After` (the onboard 429 is asserted without it). No other header (such as `Content-Type`) and no status the harness cannot reach (a real 500) is checked.

The fixtures cover success, empty collection/full replacement, authentication rejection/outage, validation, missing records, stale/closed conflicts, oversized writes, quota refusal, and missing migration fallback. Read-only endpoints do not receive bodies and do not emit payload-too-large; a missing detail is a 404 rather than an empty success. Household PUT cannot return an empty saved object: its empty request returns all seven booleans false. Onboarding without 0016 returns a null home context. `feature_unavailable` is a non-retryable 503, distinct from a retryable auth outage. Per-route responses list actual handler statuses; the shared envelope covers the remaining error codes used across HALO.

Run `node --test test/contractsB01.test.mjs`. Routes run through the isolated harness with synthetic identities, fake provider responses and fake database RPCs; the separate PGlite suites test migrations, real RPC behaviour, route wiring and database ownership. These are local contracts, not a live integration or source-rights verification.

Request schemas document structural constraints and canonical examples. Runtime parsing additionally trims text, normalizes legacy answers, uses the current calendar year, checks token ownership and enforces byte limits. Use the route validators for these context-dependent rules. Response schemas are strict about fields, including preventing owner/request-marker disclosure in home summaries.
