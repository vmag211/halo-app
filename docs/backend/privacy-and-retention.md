# B01 privacy and retention inventory

Status: **Proposed disclosure, awaiting Vibhav's approval**. Written 2026-10-10.
This describes repository behaviour, not a verified production policy. The baseline is reconstructed, not captured from Supabase. Migrations 0015 and 0016 are written and tested locally, not applied by this work. Audit the deployed schema with `docs/backend/baseline-audit.sql` before rollout.

**Sensitive input (test results, attachments, fish notes, observations) stays disabled until this document and the recovery decision are approved.** See [the recovery decision](decisions/B01-optional-recovery.md). This is a release gate, not a claim that a new capabilities endpoint enforces it; these future sensitive-input features have no implementation here. The existing symptom journal is inventoried below.

## Personal table inventory

Export and clearing are the B07 privacy routes (the spec numbers them B12): `privacy.inspect`, `privacy.export` and `privacy.clear`, governed table by table by `lib/privacyInventory.js`, whose structural tests fail when a new owned table is not placed for both (Ruling P2, P12). The last column gives each table's export group and tier (the base tier always; the private tier only when the person selects private text) or why it is never exported, and what Clear Journal and clear all do to it. Columns not named are never read: the export uses allowlists, never `select *` or a pattern. `profile_id` is never exported. Other read APIs are not an export. No age, birthdate or person name is deliberately requested. Presence bands and symptom logs can nonetheless reveal sensitive household facts. Ownership is always the verified token's user id, never a supplied owner id.

## Privacy requests (B07): export, clear and what they keep

Repository behaviour of `GET /api/privacy/status`, `POST /api/privacy/export/inspect`, `POST /api/privacy/exports`, `POST /api/privacy/clear` and the privacy half of `GET /api/operations` (plan `docs/backend/plans/b07-privacy.md`). Migration 0024 is not applied anywhere and `HALO_PRIVACY_REVIEW_KEY` is set in no environment, so none of this runs in production yet; until the key is set the panel says "Privacy requests are unavailable." (Ruling P18).

- **Review token** (P6, P10): stateless, signed with `HALO_PRIVACY_REVIEW_KEY`, binding the household, the scope, the selection and a fingerprint of the records the person's own actions write. It lives ten minutes and is stored nowhere. It carries no household identifier and no fingerprint.
- **Export file** (P8, P9): built in the request and returned inline, never stored, at any point. A lost answer is rebuilt from the stored selection and the current rows only within ten minutes of the export; after that the receipt is answered without the file. The file carries the rounded home location and the confirmed email (D-P5), never `address`, `zip` or a household identifier. Stored text (a note, a title, a Luna answer) is exported verbatim. A selection whose file would pass 4,000,000 bytes is refused at review; the person chooses fewer groups.
- **Receipts** (P10): ordinary ledger rows in domain `privacy` holding only `{operationId, status, scope}` (an export's also its two group names and private-text choice, no content). Each is purged 24 hours after it settles: lazily on every `privacy.status` read for that household, and for every household once a day by the daily cron. Pending rows are never purged; the reaper owns them. **Proposed, awaiting decision (D-P3, plan Open question 1):** these three periods are the shortest the contract allows.
- **Clear Journal** (D-P4, P13) removes `symptom_logs` and season-summary alerts. Week journal check-ins are not stored on the server yet, so nothing is removed for them, and the review says so. When the workspace package stores them they must join Clear Journal (a tripwire test enforces it).
- **Clear all** (D-P1, P3, P4) removes every household-owned record and resets the profile, in one database transaction that also settles its own receipt, so a deletion exists if and only if its request is `succeeded`. It keeps the login, the recovery challenges and its own receipt (gone 24 hours later). It is not account deletion (`DELETE /api/account` remains that path).
- **Limits** (UI-192, BE-312, BE-379): copies already downloaded cannot be recalled, and server backups and records held by service providers (auth provider internals, logs, the rate-limit store) are outside this deletion.
- **Residual F2:** a daily cron iteration that read a household's profile before its clear can still insert one `alerts` row after it (the profile row survives, so the foreign key holds). Daily scores cannot (their home context is gone) and Luna cannot (its conversation is gone). The window is one household's cron iteration; accepted and recorded (plan Open question 10). A My Week save claimed after the clear's busy check can likewise land after it: a new, deliberate save from another device.
- **Residual F3:** a clear and a concurrent My Week commit can deadlock (the commit holds its ledger row and waits on the profile the clear holds). Postgres aborts one, and the aborted one is an honest `failed` under P3 and B06 H8. Reasoned on paper: PGlite has one connection.

## Outside the table inventory

Browser Supabase sessions live in localStorage. Frontend caches/drafts are scoped by identity; changing identity clears their accessible cache namespace. Account deletion callers must clear local session/cache state after success. The deletion route is not a claim to remotely erase every device cache or downloaded file.

The submitted address is transiently sent to Mapbox for geocoding and its precise geocoded point to service-area lookup before rounding for storage; it is not saved by current onboarding. What the assistant sends to model providers is listed in the next section. `assistant_corpus` stores public passages, not transcripts: nothing in the assistant route or `lib/assistantRag.js` writes a question or an answer to the database. Provider retention, application/platform logs, auth internals and backups are separate from database cascades and have not been audited. Upstash rate-limit counters are outside Postgres and have limiter-specific windows, not a household export or deletion implementation. The assistant's keys include the verified user id (`assistant:<user id>`, `app/api/assistant/route.js`), so that id leaves to the rate-limit store. Do not place secrets or private row contents in logs, fixtures or this disclosure.

## Assistant: what leaves the app

Derived from `app/api/assistant/route.js`, `lib/assistantContextData.js`, `lib/assistantContext.js` and `lib/assistantRag.js`. This is repository behaviour. It does not describe the live deployment, whose configuration this work does not read or change.

**The code default is to send household context.** The route computes `sendContext = process.env.ASSISTANT_SEND_HOUSEHOLD_CONTEXT !== 'false'`. Context is withheld only when the variable is exactly the string `false`. An unset, empty or any other value sends it. `docs/backend-progress.md` (an older September status) records production as `false`, and `.env.example` is said to document the same (it was not opened here: the B01 boundary excludes `.env*` files). Neither is verified for the live deployment, so the live setting is unknown to this work and must be checked in the hosting configuration before anyone relies on "household context is not sent".

**Sent for every question that reaches the model pipeline, whatever the flag says** (a model key is configured, the structural diagnostic check does not decline the question, and the rate limits allow it). The question text the person typed (up to 1,000 characters, so anything personal they type leaves the app) goes to the embedding endpoint and again to the chat endpoint. The page the assistant was opened from (one of today, home, homeguard, map, journal, act, settings, learn) goes into the system prompt. The endpoints default to OpenAI-compatible addresses and can be redirected with `ASSISTANT_EMBED_URL` and `ASSISTANT_CHAT_URL`; `docs/backend-progress.md` says production uses OpenRouter's free tier and that free models may log prompts. The question's embedding vector is also passed to the database retrieval function `match_assistant_corpus`, and is not stored. With no model key configured the route answers "no source" before any of this is sent, and a declined diagnostic question sends nothing.

**Sent only when the flag allows it.** A `HOUSEHOLD CONTEXT` text block built for the verified user. Each section is left out when its data is missing, and the page decides the section order. The block can contain exactly this and nothing more:

- Today's readings (`daily_scores`, today's date): the date; the air quality index with its severity word and whether it was measured at a nearby monitor or modeled; the UV index with its severity word; the dominant pollen category (tree, grass or weed) with its severity word and 0 to 5 index; the mold risk severity word.
- Home assessment (only when the profile has a county): the home score and severity word (not for a private well or spring); a statement that the water is a private well or spring when `water_source` is one of those; otherwise the water utility name with its worst contaminant (name, measured value and limit in ppt, and whether the limit is a federal limit or a health benchmark), or a statement that no regulated contaminant is above its limit; the county name and EPA radon zone, only where the county has a zone (North Carolina counties); the lead risk word, estimated from the home's build year (the year itself is not sent); and up to three action titles ("Filter your drinking water for" a named contaminant, "Test for lead, and filter your tap water meanwhile", "Test your home for radon"). The titles are chosen and ordered using the household presence bands and renter mode (a toddler or pregnancy band moves water and lead up), so the list can indirectly hint at those facts although no band is named.
- Journal (only when there are entries in the last 90 days): for the last 13 days, at most 14 entries, each a date with up to five symptom names; and "Pattern" sentences of the form "On days with elevated" a factor "you logged symptoms" some percent "of the time, versus" another percent "on other days", computed from 90 days of entries and readings.

**Not sent to model providers:** Journal notes (the query never selects that column), symptom severity, the illness flag, household presence bands as such, the profile id, coordinates, the address or ZIP, push endpoints and email. The assistant reports `uses_household_data` when its answer cites the household block.

## Decisions and proposed periods

No new retention period is enforced by B01. **Decided by Vibhav on 2026-10-19:** settings preference rows (`public.profile_preferences`, 0021), saved discovery areas (`public.explore_areas`, 0022), My Week tasks, their planning details and task preferences (`public.household_actions`, `public.household_action_preferences` and `public.household_action_state`, 0023), Luna conversations, turns and runs (0020), and each day's recorded environmental maximum (`public.daily_maxima`, 0025, B08) are kept until the person deletes them (a task, a cleared conversation, a cleared area) or deletes the account, with no timed purge and no inactivity policy. His reason: the expected user base is small. **Proposed, awaiting decision:** Vibhav must still choose retention and any inactivity policy separately for journals, home/location history, environmental history (the app-time readings in `daily_scores`; the daily maxima are decided above), alerts, abandoned anonymous accounts, settled operation receipts and recovery challenges, backups/logs and future uploads/exports/transcripts. No numeric default is selected here. Any approved period needs implementation, purge tests, deletion/restore handling and disclosure before it is described as enforced. The commented 30-day anonymous cleanup in 0001 is not a promise of deletion.

HO-144 source-specific retention/licensing remains unverified and can override a general household period; B02/B03 must reconcile provider rules with historical data, exports and model use. Future private files require approved storage/scanning, ownership, deletion and retention rules. B12 must inventory all new nested records/objects and prove no cross-household export or deletion. Account deletion cascades are checked locally in three ways: a real-database run for `home_contexts` and `daily_scores` (`test/homeContextDb.test.mjs`), the account route against the fake harness (`test/routeIsolationFlows.test.mjs`), and, for every other table, parity between each declared owner cascade and the migrations (`test/haloTables.test.mjs`), which is not a real-database run. Live migration state, provider copies and backups remain human verification items.
